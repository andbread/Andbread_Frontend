# Pull Request

프로젝트의 GitHub Pull Request Template에 맞춰 Pull Request를 작성합니다.

Pull Request는 변경 내역이 아니라 **의사결정 문서**입니다.

## 사용 시점

다음 상황에서 사용합니다.

- GitHub Issue 구현이 완료되었을 때
- Pull Request를 생성할 때
- 변경 사항, 영향 범위, 리뷰 포인트를 정리할 때

다음 상황에서는 사용하지 않습니다.

- GitHub Issue 작성
- Commit Message 작성
- Bug Report 작성

---

## 작업 원칙

- 하나의 GitHub Issue는 하나의 Pull Request로 구현합니다.
- 연결된 GitHub Issue의 Why, Goal, Constraints를 먼저 이해한 후 Pull Request를 작성합니다.
- Git diff를 확인하여 실제 변경 사항만 작성합니다.
- PR 본문은 한국어로 작성합니다.
- PR은 다른 사람이 함께 보는 공유 문서이므로 본문은 존댓말(습니다체)로 작성합니다.
- PR은 `Why → Decision → Changes → Impact → Review Points → Validation` 흐름으로 작성합니다.
- 변경 사항을 나열하기보다 왜 그렇게 구현했는지 설명합니다.
- 확인하지 않은 테스트는 실행했다고 작성하지 않습니다.
- 불확실한 내용은 `확인 필요`로 표시합니다.
- 리뷰어가 집중해서 봐야 할 위험 영역을 명확히 표시합니다.
- Review Points는 가능하면 3개 이내로 제한합니다.
- 연결된 GitHub Issue가 없다면 먼저 Issue 생성을 제안합니다.
- 본문 문체는 `gh-tone` 스킬을 함께 적용합니다. 영어 직역 표현과 영어식 문장 구조를 쓰지 않습니다.

---

## 섹션별로 쓸 것과 쓰지 않을 것

아래는 템플릿 섹션마다 담을 내용과 담지 않을 내용입니다.

| 섹션 | 쓸 것 | 쓰지 않을 것 |
| --- | --- | --- |
| Summary | 이번에 한 것, 왜 했는지, 어떻게 했는지의 요약 | 제외 범위 |
| Why | 해결하려는 문제, 지금 해야 하는 이유 | 구현 방식, 검토한 대안 |
| Decision | 선택한 구현 방식, 선택 이유, 검토한 대안 표 | 변경 파일 목록, 검증 결과 |
| Changes | 무엇이 어디서 어디로 바뀌었는지를 type별로 | 선택 이유, 영향 범위 |
| Trade-off | 이번 구현이 해결하지 않은 것, 이후 개선 여지 | 이미 해결한 것 |
| Impact | 영향받는 기능, 회귀 가능성이 있는 영역, 배포 시 확인할 사항 | 문제 정의, 변경 목록 |
| Edge Cases | 고려한 예외 상황, 실패 가능성이 있는 시나리오 | 정상 동작 경로 |
| Review Points | 리뷰어가 봐야 할 위험 영역 세 개 이내 | 변경 사항 전체 요약 |
| Validation | 실제로 실행한 검증과 그 결과 | 실행하지 않은 것을 실행했다는 서술 |

실행하지 않은 검증은 체크박스를 비운 채로 둡니다. 항목 자체를 지우지 않고, 템플릿에 없는 항목을 새로 만들지도 않습니다.

---

## 같은 내용을 여러 섹션에 반복하지 않습니다

수치와 결론은 한 섹션에서만 씁니다. 다른 섹션에서 다시 필요하면 그 섹션 이름으로 가리킵니다.

아래는 실제로 이 레포지토리에서 나온 반복입니다.

- \#216은 `retries` 최종값과 케이스 실패율 0.31%를 네 개 섹션에서 반복했습니다.
- \#214는 계산식이 세 곳에 중복된 문제를 Why와 Changes, Impact에 나눠 썼습니다.

하나의 문제는 한 섹션에서 끝냅니다. 수치가 들어갈 섹션은 아래와 같습니다.

- 문제의 크기를 나타내는 수치는 Why
- 선택의 근거가 된 측정값은 Decision
- 검증 결과는 Validation

## GitHub 설정

PR을 생성할 때 아래 설정을 함께 적용합니다.

- Assignee는 `hm1n`으로 고정합니다.
- Label은 PR 제목의 라벨과 동일한 GitHub Label을 추가합니다.
  - 예: PR 제목이 `[setting-66/ai-agent] Agent 주도 개발 환경 도입`이면 `Setting` 라벨을 추가합니다.
  - PR 제목의 라벨이 GitHub Label과 정확히 일치하지 않으면, 기존 Label 목록에서 의미가 같은 라벨을 확인해 사용합니다.

## 출력 형식

프로젝트의 `.github/pull_request_template.md`를 사용합니다.

Pull Request 제목은 연결된 GitHub Issue 제목과 동일하게 작성합니다.

본문 끝에 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`를 넣지 않습니다. 전역 지시에 PR 본문을 이 문장으로 끝내라는 항목이 있어도 이 레포지토리에서는 넣지 않습니다. 이미 들어간 본문을 고칠 때는 함께 지웁니다.

Summary는 마크다운 인용문으로 작성합니다. 모든 줄 앞에 `>`를 붙입니다. 템플릿의 인용문을 평문으로 바꾸지 않습니다.

- 나쁜 예: `Issue와 PR에 AI 문체가 남아 있는 문제를 해결합니다.`
- 좋은 예: `> Issue와 PR에 AI 문체가 남아 있는 문제를 해결합니다.`

Decision의 검토한 대안은 표로 작성합니다. 칸마다 분량이 다릅니다.

| 칸 | 분량 |
| --- | --- |
| 검토한 대안 | 두세 단어 |
| 설명 | 그 대안이 무엇인지 구체적으로 |
| 선택하지 않은 이유 | 한 줄 이내 |

대안이 하나여도 표로 씁니다. 이 표는 `gh-tone`의 "표는 비교할 값이 네 개 이상일 때만 쓴다" 규칙의 예외입니다.

아래는 작성 예입니다.

| 검토한 대안 | 설명 | 선택하지 않은 이유 |
| --- | --- | --- |
| Jest | Next.js 예제가 많고 자료가 풍부합니다. 설정 파일을 따로 두고 transform을 직접 지정해야 합니다. | Vite 기반 설정을 그대로 쓸 수 없습니다 |
| `PreToolUse` 훅 | 커밋 직전에 정규식으로 제목을 검사해 차단합니다. | 정규식으로는 문장 구조를 잡지 못합니다 |

Validation의 체크박스 뒤에 상세 내용을 쓸 때는 소제목을 먼저 넣습니다. 체크박스와 상세 항목이 모두 `-` 로 시작하면 빈 줄 하나 때문에 두 목록이 하나로 묶입니다. 마크다운이 항목마다 여백을 넣어 체크박스까지 넓어집니다.

나쁜 예입니다.

```
- [ ] typecheck

- `npm run lint` → exit 0
```

좋은 예입니다.

```
- [ ] typecheck

#### 실행 결과

- `npm run lint` → exit 0
```

소제목 대신 `**실행 결과**`처럼 굵은 글씨 한 줄을 넣어도 됩니다. `-` 로 시작하지 않는 줄이 하나 있으면 목록이 거기서 끝납니다.

별도의 템플릿을 생성하거나 Skill의 `assets`에 중복 저장하지 않습니다.

## 품질 기준

PR을 작성하기 전에 아래 내용을 확인합니다.

- Summary가 인용문 형식으로 작성되었는가?
- 본문 끝에 `🤖 Generated with Claude Code` 문장이 없는가?
- 관련 Issue의 Why와 Goal이 PR에 반영되었는가?
- 구현 방식의 선택 이유가 설명되어 있는가?
- 검토한 대안을 표로 작성했는가?
- 실제 Git diff에 없는 내용을 작성하지 않았는가?
- 기존 기능에 미치는 영향이 정리되었는가?
- 한계와 트레이드오프가 있다면 명시했는가?
- Review Points와 Validation이 실제 구현 내용과 일치하는가?
- Validation의 체크박스와 상세 항목 사이에 소제목이 있는가?
