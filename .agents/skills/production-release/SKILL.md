# Production Release

프로덕션 릴리즈를 준비할 때 사용하는 스킬입니다.

## Workflow

1. 원격 브랜치와 태그를 최신 상태로 조회합니다.
2. 최신 버전 태그와 현재 `develop`, `main` 상태를 확인합니다.
3. 최신 태그 이후 `develop`에 병합된 PR을 수집합니다.
4. 각 PR의 번호, 제목, 라벨, `Summary`를 읽습니다.
5. `Summary`만으로 사용자 영향이 불명확한 경우에만 `Impact`를 확인합니다.
6. PR 본문만으로 판단하기 어려운 경우에만 제한적으로 Diff를 확인합니다.
7. 관련 PR을 기능 또는 목적 단위로 묶어 릴리즈 노트를 작성합니다.
8. 변경 유형과 최신 태그를 기준으로 다음 버전을 제안합니다.
9. 버전 중복과 변경사항 누락 여부를 검사합니다.
10. `npm run lint`, `npm run build`를 실행합니다.
11. 검증에 성공하면 `references/release-note.md`의 템플릿에 따라 `develop → main` 릴리즈 PR을 생성합니다.

## Release Scope

- 최신 태그가 가리키는 커밋 이후 `develop`에 포함된 변경을 대상으로 합니다.
- 기본적으로 base가 `develop`인 merged PR을 수집합니다.
- 릴리즈 PR, merge-only PR, 중복된 PR은 제외합니다.
- `develop`과 `main` 사이에 릴리즈할 변경이 없으면 PR을 생성하지 않습니다.

## Pull Request Context

PR 정보는 아래 순서로 확인합니다.

1. PR 번호
2. PR 제목
3. PR 라벨
4. PR 본문의 `Summary`
5. 필요한 경우 `Impact`
6. 필요한 경우 Diff

다음 경우에만 Diff를 확인합니다.

- `Summary`가 없거나 실제 변경 결과를 설명하지 않는 경우
- PR 제목과 `Summary`가 충돌하는 경우
- 보안, 데이터 구조, 호환성 파괴 변경이 포함된 경우
- 버전 제안에 필요한 정보가 부족한 경우

## Version Rules

버전 형식은 `vX.Y.Z`를 사용합니다.

- `major`: 기존 기능과 호환되지 않는 변경 또는 주요 사용자 흐름의 파괴적 변경
- `minor`: 새로운 사용자 기능, 공개 페이지, 사용자 흐름 또는 기존 기능의 의미 있는 확장
- `patch`: 버그 수정, 기존 기능 개선, 성능, 접근성, SEO, 내부 안정성 개선

여러 변경 유형이 함께 있으면 가장 높은 버전을 선택합니다.

`major > minor > patch`

다음 조건을 확인합니다.

- 제안한 버전 태그가 이미 존재하지 않는지 확인합니다.
- 최신 태그보다 낮거나 같은 버전을 제안하지 않습니다.
- PR 제목과 본문의 버전이 동일한지 확인합니다.
- 태그가 없는 경우 버전을 자동 결정하지 않고 사용자 확인이 필요하다고 알립니다.

## Missing Change Check

수집한 모든 PR은 다음 중 하나의 상태를 가져야 합니다.

1. 주요 변경사항에 반영
2. 다른 PR과 통합하여 반영
3. 내부 변경 또는 중복으로 제외

반영 또는 제외 사유가 없는 PR이 있으면 릴리즈 PR을 생성하지 않습니다.

`포함된 Pull Request` 섹션에는 이번 릴리즈 범위의 PR을 빠짐없이 작성합니다.
