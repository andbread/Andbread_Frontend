## 2. 관측

### 2.1 빈 토픽만 접속해도 약 4.08초 (실험 1)

새 소켓에서 `realtime:`에 한 번만 접속하고, 첫 응답을 받으면 소켓을 닫았다. 정상 토픽 접속도, 메시지 삽입도 하지 않았다. 두 방법을 ABBA 순서로 12회씩 번갈아 실행했다.

| 계측 방법 | n | 최소 | 중앙값 | 최대 |
|---|---|---|---|---|
| 독립 Node 클라이언트 (`performance.now`) | 12 | 4074.8 | **4077.0** | 4145.6 |
| 브라우저 CDP 프레임 timestamp | 12 | 4074.0 | **4076.4** | 4085.2 |
| 브라우저 페이지 안 `performance.now` | 12 | 4075.7 | 4078.7 | 4087.3 |
| Playwright 콜백 `Date.now` (기존 방식) | 12 | 4077.0 | 4086.0 | 4094.0 |

응답은 24회 모두 `status=error reason=TopicNameRequired`였다. 브라우저는 기존 추적과 같게 CPU 4배 제한을 걸었다.

### 2.2 대기의 크기와 소켓 전체의 막힘 (실험 1b)

Phoenix 소켓은 `phoenix` 토픽의 heartbeat를 채널을 거치지 않고 바로 응답한다(5.2절). 이를 기준 왕복 시간 측정과 막힘 탐지에 썼다.

| 항목 | n | 중앙값 | 범위 |
|---|---|---|---|
| 평소 heartbeat 왕복 | 36 | 75.9ms | 74.0~175.3 |
| 빈 토픽 요청 → 오류 응답 | 12 | 4077.7ms | 4074.9~4181.8 |
| 오류 응답 − 해당 회차 heartbeat 왕복 중앙값 | 12 | **4001.1ms** | 3957.8~4105.9 |
| 빈 토픽 요청 1.0초 후 보낸 heartbeat의 응답 − 오류 응답 | 12 | **0.1ms** | 0~0.5 |
| 빈 토픽 요청 2.5초 후 보낸 heartbeat의 응답 − 오류 응답 | 12 | **0.1ms** | 0~0.7 |
| 오류 응답 뒤 heartbeat 왕복 | 12 | 74.7ms | 73.9~77.8 |

**빈 토픽 요청을 기다리는 동안 보낸 heartbeat는 24회 모두 오류 응답 바로 뒤에 왔다.** DB와도, 채널과도 무관한 제어 프레임까지 밀린다는 뜻이다.

### 2.3 같은 소켓에서만 메시지가 밀린다 (실험 2 raw)

독립 클라이언트로 정상 채널에 접속하고 `phx_reply ok`와 `system ok`를 확인했다. 그 뒤 빈 토픽 접속을 시작하고, 0.5초·2.0초·3.5초 뒤에 메시지를 삽입했다. 조건마다 삽입 시점 3개 × 10회로, 조건 순서는 회차마다 돌렸다. 아래 표의 수치는 **삽입 요청 시작부터 `postgres_changes` 프레임 도착까지**의 시간이다.

| 조건 | 삽입 시점 | 삽입 시 빈 토픽 대기 중 | 중앙값 (범위) | 프레임 − 빈 토픽 오류 응답 |
|---|---|---|---|---|
| A 같은 소켓 | 0.5s | 10/10 | **3576** (3566~3661) | **0.1** (0~0.3) |
| A 같은 소켓 | 2.0s | 10/10 | **2070** (2062~2074) | **0** (0~0.1) |
| A 같은 소켓 | 3.5s | 10/10 | **573** (570~667) | **0** (0~0.2) |
| B 별도 소켓 | 0.5s | 10/10 | 450 (278~746) | −3122 (먼저 도착) |
| B 별도 소켓 | 2.0s | 10/10 | 461 (181~757) | −1609 (먼저 도착) |
| B 별도 소켓 | 3.5s | 10/10 | 420 (241~561) | −208 (먼저 도착) |
| C 빈 채널 없음 | 0.5s | – | 489 (215~764) | – |
| C 빈 채널 없음 | 2.0s | – | 291 (199~482) | – |
| C 빈 채널 없음 | 3.5s | – | 303 (244~703) | – |

- A에서는 메시지 프레임이 30회 모두 빈 토픽 오류 응답 0~0.3ms 뒤에 왔다. 지연은 **오류 응답까지 남은 시간**(약 4077ms − 삽입 시점)을 그대로 따라간다.
- B는 C와 같은 수백 ms 범위다. 중앙값은 B 445ms, C 315ms로 차이가 있지만, 삽입 시점별로 보면 순서가 뒤바뀌기도 한다(0.5s에서는 B가 더 빠르다). 이 차이의 원인은 이 실험으로 판단하지 않는다.
- 삽입 요청 자체(요청 시작 → 응답 완료)는 전 조건 83~305ms였다. 조건에 따른 차이는 없었다.

### 2.4 정상 토픽 접속 완료 지연 (실험 2 order)

새 소켓에서 두 접속 요청을 같은 순간에 연달아 보냈다. 순서마다 10회씩 실행했다.

| 요청 순서 | 정상 접속 `ok` | 빈 토픽 `error` | `system ok` | 응답 도착 순서 (10/10 동일) |
|---|---|---|---|---|
| 빈 토픽 → 정상 | **4080ms** | 4076ms | 4336ms | 빈 error → 정상 ok → system |
| 정상 → 빈 토픽 | **83ms** | 4085ms | **4086ms** | 정상 ok → 빈 error → system |
| 정상만 | 81ms | – | 372ms | 정상 ok → system |

- 정상 접속을 **먼저** 보내면 정상 접속은 막히지 않는다. 다만 약 300ms 뒤에 와야 할 `system` 구독 완료 메시지는 빈 토픽 오류 뒤로 밀린다.
- 빈 토픽을 **먼저** 보내면 정상 접속 `ok`가 오류 응답 0~6ms 뒤에 온다.
- 기존 기록 1회차의 "오류 응답 1597ms 뒤 정상 ok"는 이번 30회에서 한 번도 재현되지 않았다. 원인은 미확인으로 남긴다.

### 2.5 앱에서의 재시도와 화면 표시 (실험 2 app)

개선 전 빌드(`P0_before`)에서 A 조건만 측정했다. B와 C는 앱을 고치지 않으면 만들 수 없다. `system ok` 이후 realtime-js 재시도가 보낸 첫 빈 토픽 접속(ref3)을 기준으로 삼아 삽입 시점을 정했다. 삽입 시점마다 10회씩 실행했다.

| 삽입 시점 | 삽입 → 프레임 중앙값 (범위) | 삽입 → 화면 표시 중앙값 | 프레임 → 화면 표시 중앙값 | 프레임 − 직전 빈 토픽 응답 |
|---|---|---|---|---|
| 0.5s | 3587 (3576~3657) | 3910 | 315 | 9.8 (2.6~48.1) |
| 2.0s | 6089 (2085~6144) | 6467 | 383 | 11.5 (5.1~21.5) |
| 3.5s | 4600 (577~4748) | 4975 | 378 | 16.0 (4.8~107.4) |

2.0s와 3.5s는 분포가 두 갈래로 나뉜다. 중앙값만으로 읽지 않는다.

| 삽입 시점 | ref3 오류 직후 도착 | ref5 오류 직후 도착 |
|---|---|---|
| 0.5s | 10회, 3576~3657ms | 0회 |
| 2.0s | 3회, 2085~2142ms | **7회, 6086~6144ms** |
| 3.5s | 2회, 577~633ms | **8회, 4596~4748ms** |

앱의 대표 타임라인(2.0s 삽입 회차, 빈 토픽 ref3 전송 기준 ms):

```
     0  → phx_join  realtime:  ref=3
  2006  ── 메시지 삽입 요청 시작
  2249  → phx_leave realtime:  ref=4   (realtime-js 재시도 타이머)
  2249  → phx_join  realtime:  ref=5
  4104  ← phx_reply ref=3 error TopicNameRequired
  4104  ← phx_reply ref=4 ok
  8092  ← phx_reply ref=5 error TopicNameRequired
  8098  ← postgres_changes (메시지)
```

- realtime-js는 ref3의 응답을 기다리는 도중에 `phx_leave`(ref4)와 새 `phx_join`(ref5)을 보낸다. ref5의 오류 응답은 **ref3 응답 뒤 약 4000ms**에 온다. ref5는 ref3이 끝난 뒤에 처리되기 시작한 것으로 보인다.
- 메시지 프레임은 30회 모두 **어떤 빈 토픽 오류 응답**의 직후(2.6~107ms)에 왔다. 앞에 걸린 빈 토픽 요청이 둘이면 4초 구간 두 번을 기다려 6초 이상이 된다.
- 삽입 시점에 대기 중인 요청이 ref3 하나뿐이어도 ref5까지 기다린 회차가 있었다(2.0s 7회, 3.5s 3회). 삽입 요청을 보낸 뒤 ref5가 메시지 이벤트보다 먼저 서버의 소켓 프로세스에 도착하면 이렇게 된다고 보면 설명된다(5.2절). 서버 안의 도착 순서를 직접 본 것은 아니다.
- 화면 표시는 프레임 도착 뒤 중앙값 315~383ms가 더 걸렸다. CPU 4배 제한과 Playwright의 폴링 대기가 섞인 값이다.

## 4. 실험으로 배제한 가설

| 가설 | 배제 근거 |
|---|---|
| 정상 토픽 접속의 Muster 대기(`@muster_join_await_ms 4_000`)가 4초의 원인이다 | 정상 토픽을 전혀 접속하지 않은 소켓에서도 빈 토픽 오류가 4077ms 걸린다(2.1절). 필수 원인이 아니다. 플래그가 켜져 있는지는 여전히 모른다 |
| 기존 4.1초는 Playwright 콜백 시각의 오차다 | CDP·페이지 시계·독립 클라이언트가 모두 일치한다(3절) |
| 공개 기본값 5000ms가 그대로 적용되고 있다 | 오류 응답에서 왕복 시간을 빼면 약 4001ms가 남는다(2.2절). 5000ms와 맞지 않는다 |
| 빈 채널이 서버 전체나 삽입 경로(DB, 복제)를 막는다 | 별도 소켓(B)에서는 빈 토픽이 대기 중이어도 메시지가 수백 ms에 온다(2.3절). 삽입 요청 시간도 조건과 무관하다 |
| 지연은 메시지 수·네트워크에 비례하는 처리량 문제다 | 같은 소켓의 지연이 "오류 응답까지 남은 시간"과 ms 단위로 일치한다(2.3절) |
| (선행 보고서에서 이미 기각) 소켓 재연결 백오프 | 이번에도 모든 회차에서 소켓은 한 번만 열렸다 |

## 5. 공개 소스로 확인한 경로

읽은 버전: `supabase/realtime` main `74f288fd`(2026-09-23, 태그 v2.137.17 시점), 그리고 이 버전의 `mix.lock`이 가리키는 `supabase/phoenix` `2d728ffe`(브랜치 `v1.8-no-drop-missing-join-refs`). **운영 서버가 이 버전인지는 모른다(6절).**

### 5.1 빈 토픽 오류는 응답 전에 잠든다

`lib/realtime_web/channels/realtime_channel.ex`

```elixir
def join("realtime:", _params, socket) do            # 49행
  socket
  |> log_error("TopicNameRequired", "You must provide a topic name")
  |> join_error()
end

defp join_error({:error, _} = error) do              # 1255행
  Process.sleep(channel_error_backoff_ms())
  error
end
```

- `log_error/3`(`realtime_channel/logging.ex`)는 로그를 남기고 `{:error, %{reason: msg}}`를 돌려준다. 따라서 `join_error/1`의 첫 번째 절이 선택되어 잠든다.
- 대기값은 `config/runtime.exs` 12행의 `Env.get_integer("CHANNEL_ERROR_BACKOFF_MS", to_timeout(second: 5))`에서 온다. `lib/realtime/application.ex` 73행에서 `:persistent_term`에 저장된다. `ENVS.md` 기준 기본값은 5000ms이고, 설명은 "채널 접속 오류를 돌려주기 전 대기, 재연결 폭주 완화용"이다.
- 이 대기는 2026-04-09 PR #1806(`feat: add channel error backoff`)에서 추가됐다. 추가 당시부터 기본값은 5초다.

### 5.2 채널 접속을 기다리는 동안 소켓 프로세스는 다른 메시지를 처리하지 않는다

`supabase/phoenix` `lib/phoenix/socket.ex` 716~760행: 소켓 프로세스의 `handle_in(nil, %{event: "phx_join"} ...)`이 `Phoenix.Channel.Server.join/4`를 **직접 호출**하고, 결과를 받아야 응답 프레임을 만든다.

`lib/phoenix/channel/server.ex` 17~58행: `join/4`는 채널 프로세스를 띄우고 나서, `{^ref, {:ok | :error, reply}}` 또는 `:DOWN`만 받는 `receive`에서 기다린다. 채널 프로세스는 `handle_info({Phoenix.Channel, ...})`(299행~)에서 `RealtimeChannel.join/3`을 실행한다. 그 안에서 5.1절의 `Process.sleep`이 끝나야 `GenServer.reply`로 응답이 돌아간다.

이 `receive`는 조건에 맞는 메시지만 꺼낸다. 그동안 소켓 프로세스 메일함에 도착한 다른 메시지는 꺼내지지 않고 남는다. 다음 요청 프레임(heartbeat, 다른 `phx_join`, `phx_leave`)과 소켓으로 밀어 넣는 이벤트가 모두 여기에 해당한다.

`postgres_changes`가 소켓 프로세스를 거친다는 것도 확인했다.
- `realtime_channel.ex` 974행: CDC 구독 메타데이터가 `{:subscriber_fastlane, transport_pid, serializer, ids, topic, is_new_api}`다.
- `lib/extensions/postgres_cdc_rls/message_dispatcher.ex`: 변경 이벤트를 인코딩해 `send(fastlane_pid, encoded_msg)`로 **소켓 프로세스(`transport_pid`)에 직접** 보낸다.

2.2~2.5절의 관측은 모두 이 구조로 설명된다. heartbeat, 뒤따른 정상 접속, `phx_leave`, 재전송된 `phx_join`, `system`, `postgres_changes`가 전부 소켓 프로세스의 같은 메일함을 거치기 때문이다. 별도 소켓(B)은 다른 프로세스이므로 영향이 없다.

### 5.3 클라이언트가 대기 중에도 재전송한다

`@supabase/realtime-js` 2.89.0 `dist/main/RealtimeChannel.js`

```js
_rejoinUntilConnected() {        // 589행
    this.rejoinTimer.scheduleTimeout();   // 다음 재시도를 먼저 예약한다
    if (this.socket.isConnected()) {
        this._rejoin();
    }
}
_rejoin(timeout = this.timeout) { // 620행
    ...
    this.socket._leaveOpenTopic(this.topic);  // 같은 토픽의 접속 중 채널에 phx_leave
    this.state = constants_1.CHANNEL_STATES.joining;
    this.joinPush.resend(timeout);            // 새 phx_join
}
```

재시도 타이머는 `reconnectAfterMs`(1s, 2s, 5s, 10s 계단)를 쓴다. 이전 요청의 응답을 기다리는지는 따지지 않는다. 그래서 2.5절처럼 `phx_leave`와 `phx_join`이 대기열에 쌓인다.

## 6. 운영 서버에 대해 남는 추정

| 항목 | 상태 |
|---|---|
| 운영 Realtime 배포 버전 | **미확인.** 웹소켓 핸드셰이크 응답 헤더에는 `sb-gateway-version: 1`, `sb-project-ref` 등만 있고 Realtime 버전은 없다. 이 세션에서는 Supabase 관리 화면에 접근하지 않았다 |
| 운영 `CHANNEL_ERROR_BACKOFF_MS` 값 | **미확인.** 관측값(왕복을 뺀 약 4001ms)은 "4000ms로 설정된 `join_error` 대기"와 맞는다. 그러나 공개 기본값 5000ms와는 다르다. 설정값을 확인한 것은 아니다 |
| `use_muster_channel_join` 플래그 | 미확인. 4초의 필수 원인이 아님은 측정으로 확인했다(4절) |
| 소켓 프로세스의 내부 대기 | 프레임 순서로 "같은 연결의 모든 프레임이 오류 응답 뒤로 밀린다"는 것까지만 관측했다. 서버 프로세스 안을 직접 본 것은 아니다 |
| 자체 호스팅 재현 | 이번 범위에서 제외했다(후속 과제). 운영 버전과 설정을 모르므로, 재현하더라도 운영 서버의 증명으로 쓰지 않는다 |

**운영 환경에 대해 쓸 수 있는 표현:** "빈 토픽 접속 오류가 약 4초 뒤에 오고, 그동안 같은 웹소켓의 다른 프레임이 모두 그 뒤로 밀린다(측정). 공개 소스에는 채널 접속 오류를 돌려주기 전에 설정값만큼 잠드는 코드와, 그동안 소켓 프로세스가 다른 메시지를 처리하지 않는 구조가 있다(소스). 운영 서버의 버전과 대기 설정값은 확인하지 못했다."

**쓰면 안 되는 표현:** "운영 서버의 `CHANNEL_ERROR_BACKOFF_MS`는 4000ms다", "Muster가 원인이다", "서버 소켓 프로세스가 4초 동안 멈춘 것을 확인했다".

## 7. 선행 보고서 정정

[realtime-delay-mechanism-report.md](./realtime-delay-mechanism-report.md)는 원본으로 보존하고, 아래 내용만 이 문서로 정정한다.

| 선행 보고서 | 정정 |
|---|---|
| 5.1절 "빈 토픽 핸들러는 아무것도 기다리지 않는다. 4초는 이 함수 안에 있지 않다" | **틀렸다.** `join_error()`가 `Process.sleep(channel_error_backoff_ms())`를 실행한다(5.1절). 4초는 이 경로에 있다고 보는 것이 측정과 맞는다 |
| 5.2절 Muster 4000ms 상수를 "일치하는 후보"로 제시 | Muster 대기는 **필수 원인이 아니다.** 정상 토픽 없이도 4초가 난다(2.1절) |
| 6절 추정 9 "재시도마다 4초가 반복되는 이유" | 재시도마다 같은 빈 토픽 오류 경로의 대기를 다시 탄다. 대기 중 재전송이 겹치면 대기가 이어서 쌓인다(2.5절, 5.3절) |
| 6절 추정 10 "순서 보장이 서버와 클라이언트 중 어디서 생기는지" | 서버 쪽이다. 독립 클라이언트(realtime-js 없음)에서도 heartbeat와 메시지가 오류 응답 뒤로 밀린다(2.2절, 2.3절) |
| 6절 추정 12 "관찰 3회로는 4.1초가 다른 환경에서도 같은지 말할 수 없다" | 같은 날 다른 시각에 세 가지 계측으로 176회 반복해도 4073.8~4230.5ms였다(앞 요청을 기다린 ref5는 제외). 다른 네트워크나 다른 날짜의 재관찰은 여전히 하지 않았다 |
| 4.2절 회차 2 "대기 중인 요청이 없으면 529ms" | 유지된다. 같은 결론이 조건 C와 B로 재확인됐다(2.3절) |

## 8. 한계와 남은 질문

- 운영 서버 버전과 설정값: 지원 문의 초안을 준비했고, 발송하지 않았다.
- 자체 호스팅 재현(대기 설정 0/2000/4000/5000ms): 후속 과제로 미뤘다.
- 기존 기록 1회차의 "정상 ok가 오류 응답 1597ms 뒤" 현상: 재현되지 않았고 원인은 미확인이다.
- B와 C 사이의 중앙값 차이(약 130ms): 삽입 시점별로 방향이 일정하지 않다. 원인은 판단하지 않는다.
- 측정은 2026-09-23 오후 약 30분 동안 한 네트워크에서만 했다.
- 화면 표시 지표는 A 조건만 있고, CPU 4배 제한과 Playwright 대기 방식이 포함된 값이다.
- "정리 함수만 고치면 재시도가 멈춘다"는 선행 보고서 추정 11은 이번 범위가 아니어서 확인하지 않았다.
