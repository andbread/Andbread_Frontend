## 1. 요약

**PR #144의 개선은 실측으로 확인됐다.** 렌더 비용 지표에서 12개 셀 전부 통계적으로 유의하게 개선(p < 0.001, 효과 크기 1.00)됐고, 메시지 전송 후 화면 반영까지의 체감 지연은 **3961ms → 49ms (98.8% 감소)** 다.

동시에 계획서가 세운 가설 중 **하나는 기각**되고, 개선 효과의 귀속이 애초 가정과 달랐다. 지연의 원인은 낙관적 업데이트 부재만이 아니라 **Realtime 구독 구현 결함**이기도 했다. 이 귀속은 처음에 정황 증거에 기반한 추론이었으나, 개선 전 코드에 가드 한 줄만 추가한 조건을 따로 만든 A/B/C 실험(2026-09-02)으로 확정했다. **수신 경로는 구독 결함이 거의 전부(4219ms → 520ms)이고, 전송 경로는 구독 결함 약 1843ms와 나머지 개선 약 2133ms가 절반씩이다**(4.2절).

## 4. 예상과 달랐던 것

### 4.1 H6 기각: 낙관적 업데이트의 이득은 네트워크 품질과 무관했다

계획서는 "낙관적 업데이트가 숨기는 것은 왕복 지연이므로, RTT를 400ms 올리면 개선 폭이 커질 것"이라고 예측했다. 결과는 **N1 98.8%, N2 98.7%로 사실상 동일**했다.

이유는 Before의 지연 자체가 RTT에 둔감하기 때문이다.

| Before keydown→페인트 | 값 |
|---|---|
| 100건 / N1 | 3961.0ms |
| 100건 / N2 (RTT +400ms) | 3890.5ms |
| 300건 / N1 | 3749.6ms |

RTT를 400ms 올려도, 메시지를 3배로 늘려도 **약 3.8~4.0초에서 거의 변하지 않는다.** 즉 이 지연은 네트워크 왕복도 렌더 비용도 아닌 **거의 고정된 다른 요인**이 지배한다.

### 4.2 Realtime 구독 구현 결함이 지연의 원인임을 A/B/C 실험으로 확정했다

#### 본 측정에서 관찰된 것

S3(상대가 보낸 메시지 수신)은 낙관적 업데이트가 전혀 관여하지 않는 시나리오다. 그런데도 큰 차이가 났다.

| S3 수신→페인트(근사) | Before | After |
|---|---|---|
| 100건 / N1 | 4328.5ms | 462.3ms |
| 100건 / N2 | 4281.9ms | 457.2ms |

렌더 비용 차이는 157.6ms → 6.4ms로 151ms뿐이다. 나머지 **약 3.7초는 Realtime 이벤트가 앱에 도달하는 시간 자체의 차이**다.

Before 코드에서 확인된 결함:

```js
// Before: nbreadId 초기값이 ''
const [nbreadId, setNbreadId] = useState<string>('')

// async 함수를 호출하므로 cleanup 반환값이 React에 전달되지 않는다
useEffect(() => { subscribeChatRoom() }, [nbreadId])
```

- `nbreadId`가 `''`인 상태로 먼저 구독을 시도해 `supabase.channel('')`로 join한다. 서버는 `TopicNameRequired: You must provide a topic name` 에러로 거절하고, 클라이언트는 이 빈 토픽에 대해 join/leave를 반복한다(WebSocket 프레임에서 확인).
- cleanup이 전달되지 않아 채널이 정리되지 않고 누적된다.

#### 추론에 남아 있던 구멍

위 두 관찰만으로는 인과가 확정되지 않았다. 빈 문자열 구독은 마운트 직후 한 번 일어나는 사건인데, 본 측정은 초기 렌더 후 5초를 기다린 뒤에 메시지를 주고받았다. 마운트 시점의 경쟁 조건만으로 5초 뒤의 3.9초 지연을 설명할 수 없다.

그래서 의심 지점 한 곳만 바꾼 조건을 추가해 세 조건을 비교했다(2026-09-02).

| 조건 | 코드 |
|---|---|
| A_before | PR #144 역적용, 개선 전 원본 |
| B_guard | 개선 전 원본에 `if (!nbreadId) { return }` 가드 한 줄만 추가 |
| C_after | 개선 후 |

B는 A와 정확히 한 줄만 다르고 렌더 최적화도 낙관적 업데이트도 없다. 따라서 **A와 B의 차이는 전부 빈 토픽 구독의 몫**이고, **B와 C의 차이는 나머지 개선 축의 몫**이다. 계측은 앱 코드를 건드리지 않고 `page.on('websocket')`으로 프레임 도착 시각을 밖에서 관측해 세 조건에 동일하게 적용했다.

#### 수신 경로: 빈 토픽 구독이 원인으로 확정

n=20, 중앙값. 실패 1건(A_before 0회차 30초 타임아웃).

| 조건 | 전체 지연 | 프레임 도착까지 | 도착 후 페인트 | 렌더 합 | `TopicNameRequired` |
|---|---|---|---|---|---|
| A_before | 4550.0ms | 4219.0ms | 320.0ms | 247.1ms | 2 |
| B_guard | **903.0ms** | **520.0ms** | 396.5ms | 260.0ms | 0 |
| C_after | 596.5ms | 536.0ms | 131.0ms | 7.8ms | 0 |

가드 한 줄로 전송 구간이 4219ms → 520ms가 되어 After(536ms)와 사실상 같아졌다. `TopicNameRequired` 프레임도 0건이 됐다. B의 렌더 합이 A와 같은 수준(260.0 vs 247.1ms)이므로, 줄어든 시간이 렌더가 아니라 전송 구간에서 나온 것도 확인된다. 사전 판정 규칙("B가 1초 안쪽")을 충족하므로 **수신 경로의 원인은 빈 토픽 구독으로 확정한다.**

#### 전송 경로: 두 원인이 절반씩

n=20, 중앙값. 실패 0건.

| 조건 | 전체 지연 | 프레임 도착까지 | 도착 후 페인트 | 프레임 관측 |
|---|---|---|---|---|
| A_before | 4171.0ms | 3471.5ms | 601.0ms | 20/20 |
| B_guard | **2328.0ms** | 1326.5ms | 1021.0ms | 20/20 |
| C_after | **195.0ms** | 관측되지 않음 | 해당 없음 | 0/20 |

가드 한 줄이 4171ms를 2328ms로 줄였다(−1843ms). 그러나 1초 아래로 떨어지지도, 3초 이상 남지도 않아 **사전 규칙 두 개 사이에 값이 떨어졌다.** 규칙이 판정을 내려주지 못했고, 결론은 두 원인이 모두 유의미하게 기여했다는 것이다.

전송 경로에는 수신에 없는 단계가 하나 더 있다. Before는 Enter 후 `insertChatMessage`의 저장 응답을 기다리고, 그다음 Realtime 에코를 또 기다린 뒤에 그린다. 구독을 고쳐도 이 왕복은 남으므로 B에 1326.5ms가 남았다.

C는 20회 모두 프레임이 관측되지 않았다. 195ms에 이미 페인트가 끝났고 스크립트가 곧바로 컨텍스트를 닫으므로, 뒤늦게 오는 에코를 볼 기회가 없었다. 사전 규칙은 "프레임 도착보다 페인트가 먼저(음수)"라는 문구였는데 실제로는 프레임 자체가 안 잡히는 형태로 나왔다. **문구를 글자 그대로 충족한 것은 아니지만, After가 서버를 기다리지 않는다는 같은 결론을 보여준다.**

#### 지연 분해

| 항목 | A_before | B_guard | C_after |
|---|---|---|---|
| 서버 왕복과 에코 대기 | 3471.5ms | 1326.5ms | 대기하지 않음 |
| 도착 후 렌더하여 페인트 | 601.0ms | 1021.0ms | 해당 없음 |
| 전체 체감 지연 | 4171.0ms | 2328.0ms | 195.0ms |

- A → B: 빈 토픽 구독 제거만으로 **−1843ms**
- B → C: 낙관적 업데이트가 왕복 대기를, 메모이제이션이 도착 후 렌더를 걷어내 **−2133ms**

**의미**: 개선 효과를 어느 한쪽에 귀속하면 틀린다. 수신 경로는 구독 결함이 거의 전부지만, 전송 경로는 구독 결함과 나머지 개선이 대략 절반씩이다. 기존 블로그는 구독 결함 쪽을 전혀 다루지 않았고, 이 보고서의 이전 판(2026-09-01)은 반대로 구독 결함을 전송 경로의 주범으로 과대 귀속했다.

#### 해석에 쓸 수 없는 값

`actualDurationSum`은 전송 시나리오의 지연 분해에 쓸 수 없다. 회차마다 입력창을 채우기 직전에 초기화하는데 `page.fill`이 유발하는 리렌더가 Enter 이전에 발생하므로, A·B의 2110.1ms·2235.4ms에는 측정 구간 밖의 렌더가 섞여 있다(커밋 수 A·B 5회, C 2회). 측정 구간 내 렌더 비용은 `frameToPaint`로 상한을 잡는다.

B의 `frameToPaint`(1021.0ms)가 A(601.0ms)보다 큰 이유는 확인하지 못했다. IQR이 566.8~1206.8ms로 넓다. 이 값 위에 추가 결론을 세우지 않는다.

#### 다른 측정과의 비교 금지

C의 195.0ms는 본 측정 S2의 49.2ms보다 크다. 본 측정은 페이지 안에서 `keydown` 시각을 기록했고 이 실험은 브라우저 밖 Node의 `Date.now()`를 썼으므로 프로세스 간 지연이 섞인다. **실험 내 A·B·C 비교는 유효하지만 다른 측정의 절대값과 나란히 놓으면 안 된다.**

#### 남은 미확인 사항

- 실패한 채널 하나가 왜 다른 채널의 이벤트 전달까지 늦추는지, supabase-js 내부 동작은 규명하지 않았다.
- cleanup 누락(채널 누적)의 기여를 분리하지 않았다. B는 cleanup 누락을 그대로 둔 채로도 수신 지연이 After 수준까지 떨어졌으므로 누적의 기여가 작았음을 시사하나, 누락만 고친 네 번째 조건으로 확인하지는 않았다.

### 4.3 초기 진입(S1)은 렌더는 빨라졌지만 체감은 거의 그대로다

| S1 | Before | After | 개선 |
|---|---|---|---|
| 렌더 비용 (300건) | 362.7ms | 65.6ms | 81.9% |
| 진입 완료까지 (300건) | 2351ms | 2138ms | 9.1% |
| 진입 완료까지 (100건 / N2) | 4776ms | 5197ms | **-8.8%** |

초기 진입 시간은 번들 다운로드와 초기 쿼리가 지배하고, 렌더 비용은 그 일부다. 300ms를 줄여도 전체 2.3초에서 9% 수준이다.

지연 네트워크(N2)에서는 After가 **421ms 느렸다**(p=0.047, 효과 크기 0.37). After 번들이 약간 크고(322kB vs 321kB) 컴포넌트 분리로 청크 구성이 달라진 영향으로 보인다. 효과 크기가 중간 수준이고 방향이 반대이므로, **"초기 진입 속도는 이 PR의 개선 대상이 아니었고 실제로 개선되지 않았다"**로 보고한다. 개선을 원한다면 별도 작업(가상화, 청크 분할)이 필요하다.

### 4.4 `actualDuration / baseDuration` 비율은 mount 단계에서 무효

memo 차단 효과의 대리 지표로 이 비율을 쓰기로 했으나, S1(mount)에서는 Before 1.17 → After 2.98로 **거꾸로 나왔다**.

`baseDuration`은 "메모이제이션 없이 서브트리 전체를 렌더할 때의 추정 비용"이고, 이 추정은 컴포넌트 트리 구조에 의존한다. 컴포넌트를 분리하면 산정 기준 자체가 달라진다. 게다가 mount에서는 건너뛸 하위 트리가 없으므로 memo가 개입할 여지가 없다.

따라서 이 지표는 **update 단계(S2~S5)에서만** 해석한다. 거기서는 일관되게 기대대로 나왔다.

| update 단계 actualOverBase | Before | After |
|---|---|---|
| S2 / 300건 | 1.00 | 0.15 |
| S4 / 100건 | 1.00 | 0.09 |
| S4 / 300건 | 1.00 | 0.06 |
| S5 / 100건 N2 | 0.96 | 0.09 |

Before는 항상 1.00 — 하위 트리를 하나도 건너뛰지 않는다. After는 메시지가 많아질수록 비율이 더 떨어진다(0.09 → 0.06). memo가 실제로 동작한다는 직접 증거다.

### 4.5 Long Task: 메인 스레드 점유 감소

| Long Task 합계 | Before | After | 개선 |
|---|---|---|---|
| S4 / 300건 | 6883ms | 1186.5ms | 82.8% |
| S5 / 100건 | 5763.5ms | 1003ms | 82.6% |
| S2 / 300건 | 4245.5ms | 1196.5ms | 71.8% |

After의 약 1000~1400ms는 초기 스크립트 파싱·실행에서 오는 하한이며 조건과 무관하게 깔린다. 그 위에 쌓이던 Before의 추가 점유가 사라졌다.

## 5. 기존 블로그 수치와의 관계

| 항목 | 블로그 | 이번 측정 |
|---|---|---|
| 측정 환경 | 미기재 (개발 빌드 추정) | 프로덕션 빌드 + 운영 Supabase, CPU 4x, 명세 고정 |
| 반복 횟수 | 스크린샷 1~2장 | 셀당 20회, 12셀, 총 480런 |
| commit당 시간 | 41.9~77.5ms → 1~2ms | S2 commit 최대 270.8ms → 2.8ms (100건) |
| 체감 지연 | "3~4초" (수치 없음) | **3961ms → 49ms** (100건, n=20) |

절대값은 직접 비교하지 않는다. 블로그는 개발 빌드로 추정되고 이번은 프로덕션 빌드 + CPU 4x 스로틀링이다. 다만 **블로그가 서술로만 남긴 "3~4초 지연"이 3961ms로 정량 재현**됐고, 개선 방향과 크기도 블로그 주장과 어긋나지 않는다.

블로그가 보완해야 할 점은 수치 정확도보다 **귀속**이다(4.2절).

## 6. 한계

1. **자동 측정은 Headless Shell 기준**이다. 실제 Chrome(headed) 절대값은 다를 수 있다. Before/After가 동일 브라우저를 쓰므로 비교는 유효하다.
2. **S3의 수신→페인트는 근사값**이다. 삽입을 Node 프로세스에서 하고 시각은 페이지에서 재므로 프로세스 간 지연이 섞인다. 양쪽에 동일하게 섞이므로 비교는 유효하되 절대값은 상한으로 읽어야 한다.
3. **결론의 범위는 "현재 코드베이스 위에서 PR #144 변경분의 효과"**다. 2026년 5월 당시 앱 전체의 성능 차이가 아니다.
4. **기기 1대, 단일 세션**이다. 다른 기기·다른 시각의 재현성은 확인하지 않았다.
5. **초기 진입(S1)의 wallClock은 네트워크 변동에 민감**하다. N2에서 관측된 -8.8%는 청크 구성 차이일 수 있으나 원인을 확정하지 않았다.
6. `MessageItem` 렌더 횟수 0회는 자동 수집하지 않았다. `actualOverBase`가 대리 지표다.
7. **A/B/C 실험(4.2절)의 절대값은 본 측정과 비교할 수 없다.** 측정 시작 시각의 기준이 다르다. 실험 내 조건 비교만 유효하다.
8. **A/B/C 실험은 원인의 소재만 가렸다.** 실패한 채널이 다른 채널의 이벤트 전달을 늦추는 supabase-js 내부 기제와, cleanup 누락(채널 누적)의 기여분은 분리하지 않았다.
9. **이번 측정은 React DevTools를 쓰지 않았다.** React `<Profiler>` API의 `onRender` 콜백을 직접 수집했다. 데이터 출처는 DevTools Profiler가 화면에 그리는 React 프로파일링 정보와 같지만 도구가 다르므로, 지난 글의 DevTools 캡처와 이번 표의 수치를 같은 자로 잰 값으로 취급하면 안 된다.

## 7. 증거물 구성에 대한 결정

당초 계획은 React DevTools Profiler 화면 캡처를 이번 측정의 시각 증거로 남기는 것이었다. 그러나 캡처를 자동화할 수 없다는 점이 확인되어 계획을 바꿨다.

DevTools 패널은 페이지와 분리된 화면이라 Playwright로 접근할 수 없고, OS 수준으로 창을 찍으려면 그 창이 화면 맨 앞에 있어야 한다. 즉 캡처하는 동안 측정용 브라우저가 데스크톱을 점유해야 하므로 자동화로 우회할 수 있는 문제가 아니었다.

그래서 역할을 나눴다. **지난 글의 DevTools 캡처는 병목을 찾아낸 탐색 단계의 자료로 남기고, 이번 재측정의 결과는 표로 제시한다.** 두 자료는 도구와 환경이 다르므로 수치를 나란히 비교하지 않는다(6절 7항).

| | 지난 글 캡처 | 이번 재측정 |
|---|---|---|
| 목적 | 병목을 찾는 과정 | 개선 폭 검증 |
| 도구 | React DevTools Profiler (UI) | React `<Profiler>` API |
| 환경 | 개발 빌드 | 운영 빌드 + 운영 Supabase, CPU 4배 제한 |
| 횟수 | 1~2회 | 480회 |
