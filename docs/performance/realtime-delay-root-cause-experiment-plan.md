# Realtime 약 4초 지연 원인 확인 실험 계획

## 클로드 세션에 전달할 작업 요청

개선 전 채팅 코드에서 `realtime:` 빈 토픽 구독이 정상 토픽의 접속과 메시지 전달을 늦추는 경로를 확인한다. 아래 네 작업을 순서대로 진행하고, 측정으로 확인한 사실과 서버 소스에 근거한 추정을 분리해 보고한다. 기존 앱 동작과 측정 원본을 보존한다.

먼저 [기제 보고서](./realtime-delay-mechanism-report.md), [원시 프레임 기록](./results/20260923/realtime-trace.json), [기존 추적 스크립트](../../scripts/perf/trace-realtime.mjs)를 읽는다. 기존 기록의 빈 토픽 `phx_join` → `TopicNameRequired` 응답은 4079~4134ms였다. 현재 공개된 Supabase Realtime 소스의 `join_error()`는 오류를 반환하기 전 `channel_error_backoff_ms()`만큼 대기하지만, 공개 기본값은 5000ms다. **현재 기록만으로 운영 서버가 이 경로에서 4000ms를 기다렸다고 결론 내리지 않는다.** 정상 토픽의 Muster 대기와 측정 시각 오차도 별도 후보로 유지한다.

## 공통 측정 규칙

- 앱 코드는 수정하지 않는다. 새 추적 스크립트와 결과는 기존 파일을 덮어쓰지 않는 이름으로 저장한다.
- 실험용 채팅방과 계정만 사용한다. 운영 데이터에 쓰는 경우 기존 테스트 자원 생성·정리 절차를 재사용하고, 실패 시에도 해당 자원의 정리와 잔존 건수 확인을 수행한다. 접속 요청만으로 끝나는 실험에는 테스트 메시지를 만들지 않는다.
- 각 웹소켓에 별도 번호를 붙이고 `phx_join`, `phx_reply`, `postgres_changes`, `phx_leave`, 소켓 열림·닫힘의 토픽·참조값·방향·시각을 기록한다. 인증 토큰, 서비스 키, 세션값과 전체 접속 주소의 키 매개변수는 결과 파일·콘솔에 남기지 않는다.
- `Date.now()`로 Playwright 콜백이 실행된 시각만 저장하지 말고, 같은 프레임의 브라우저 프로토콜 시각도 기록한다. 브라우저 밖의 독립적인 웹소켓 클라이언트에서는 단조 증가 시계를 사용한다. 시계가 다른 프로세스의 절대 시각은 직접 빼지 않는다.
- 서버 메시지 삽입 시각은 요청 시작과 응답 완료로 구간을 표시한다. 요청 시작을 데이터베이스의 실제 삽입 완료 시각이라고 부르지 않는다.
- 조건 순서를 번갈아 바꾸고 각 조건을 최소 10회 반복한다. 재시도 중인 빈 토픽 요청이 실제로 진행 중인 회차와 아닌 회차를 구별해 분석한다. 실패·타임아웃도 원시 결과에 남긴다.

## 실험 1. 빈 토픽만 접속

새 웹소켓에서 빈 토픽 `realtime:`만 한 번 구독하고 첫 `phx_reply`를 받을 때까지 측정한다. 정상 토픽이나 메시지 삽입은 하지 않는다. 첫 응답 뒤에는 채널과 연결을 정리해 자동 재시도가 다음 회차에 섞이지 않게 한다. 같은 접속을 독립적인 웹소켓 클라이언트에서도 반복한다.

판정: 여기서도 약 4.1초가 반복되면 정상 토픽 접속과 그 안의 Muster 대기는 **빈 토픽 오류 응답 지연의 필수 원인이 아니다**. 빈 토픽만 접속하면 즉시 오류가 온다면, 기존 기록에서 함께 실행된 정상 토픽 접속이나 계측 방식이 지연에 관여했을 가능성을 조사한다. 빈 토픽 단독 응답이 약 5초라면 기존 4.1초 기록과의 차이부터 확인한다.

## 실험 2. 같은 웹소켓과 별도 웹소켓

먼저 정상 채널의 `phx_reply: ok` 및 필요한 `system: ok`를 확인한다. 그다음 빈 토픽 접속을 시작하고, 오류 응답을 기다리는 구간의 서로 다른 시점에 고유한 메시지를 삽입한다.

| 조건 | 정상 채널 | 빈 채널 |
|---|---|---|
| A | 웹소켓 1 | 웹소켓 1 |
| B | 웹소켓 1 | 웹소켓 2 |
| C | 웹소켓 1 | 없음 |

별도 Supabase 클라이언트를 쓰더라도 실제 소켓 수와 각 프레임의 소켓 번호를 확인한다. 비교 지표는 빈 토픽 요청 이후 오류까지, 삽입 요청 시작·완료, `postgres_changes` 프레임 도착, 화면 표시까지의 시간이다. 앱 렌더 영향을 줄이기 위해 프레임 도착을 우선 지표로 삼는다. 메시지는 대기 구간의 초반·중반·후반에 각각 넣어, 지연이 오류 응답까지 남은 시간에 따라 달라지는지 확인한다.

판정: A에서만 정상 메시지 프레임이 빈 토픽 오류 직후에 몰리고 B와 C에서는 빨리 오면 **간섭이 같은 연결에 국한된다**고 판단한다. 이것만으로 서버 소켓 프로세스의 정확한 대기 지점까지 확정하지 않는다. A와 B가 모두 늦으면 연결 밖의 공유 자원이나 삽입 경로를 조사한다. 세 조건이 비슷하면 재시도 구간과 실험 재현 여부를 먼저 확인한다.

초기 정상 구독 완료 응답이 늦어지는 문제도 따로 확인한다. 새 소켓에서 빈 토픽 요청 뒤 정상 토픽 요청을 보내고, 두 응답의 참조값과 순서를 기록한다. 이미 구독한 채널의 메시지 전달 실험과 혼동하지 않는다.

## 실험 3. 측정 시각 교차 검증

실험 1·2의 동일 프레임에 대해 Playwright 콜백 시각, 브라우저 프로토콜 시각, 독립 웹소켓 클라이언트의 시각을 각각 비교한다. 기존 스크립트는 `framesent`·`framereceived` 콜백에서 `Date.now()`를 호출하므로, 프레임 발생부터 콜백 실행까지의 지연이 섞일 수 있다. 각 방법에서 빈 토픽 첫 요청→오류 응답의 분포와 재시도마다 걸린 시간을 제시한다.

판정: 서로 다른 계측 방법에서도 약 4.1초가 반복되면 기존 측정값의 신뢰도가 높아진다. 약 5초로 바뀌거나 방법별 차이가 크면 시각 기록 경로를 먼저 조사하고, 4.1초를 서버 설정값의 근거로 사용하지 않는다.

## 실험 4. 운영 서버 버전·설정과 서버 코드 대조

운영 Supabase의 Realtime 배포 버전 및 `CHANNEL_ERROR_BACKOFF_MS` 값을 접근 가능한 관리 화면·공식 문서·지원 답변으로 확인할 수 있는지 조사한다. 외부에서 확인할 수 없는 값은 추정하지 않는다. 지원 문의가 필요하면 확인할 항목과 익명화한 프레임 타임라인을 담은 초안까지 준비한다. 외부에 문의를 보내는 일은 이 계획의 실행 범위에 넣지 않는다.

확인된 배포 버전의 서버 소스에서 다음 경로를 끝까지 읽는다: `join("realtime:", ...)` → `log_error` → `join_error` → 오류 응답 작성, 소켓의 `Phoenix.Channel.Server.join` 호출과 후속 프레임 처리. 현재 `main` 브랜치의 기본값을 운영 서버의 실제 값으로 취급하지 않는다. 서버 버전·설정을 얻지 못하면 동일 버전 자체 호스팅도 불가능하므로, 최신 공개 버전으로 재현하더라도 **운영 서버의 증명**으로 쓰지 않는다. 자체 호스팅이 가능하면 오류 대기 설정을 0·2000·4000·5000ms로 바꿔 빈 토픽 응답과 같은 소켓의 정상 프레임 지연이 설정값에 따라 이동하는지 확인한다.

판정: 운영 서버의 버전과 설정이 확인되고 해당 버전의 오류 처리 경로 및 계측 결과가 일치하면 내부 원인에 대한 결론을 강화한다. 값 확인에 실패하면 공개 코드에서 가능한 기제와 운영 환경에서 관측된 현상을 구분해 남긴다.

## 산출물과 결론 기준

- 새 스크립트, 조건별 원시 타임라인, 반복 측정 요약, 실패 회차 목록을 기존 결과와 별도 파일로 저장한다.
- 보고서에는 `관측`, `실험으로 배제한 가설`, `공개 소스로 확인한 경로`, `운영 서버에 대해 남는 추정`을 분리한다.
- 4.1초의 출처, 정상 토픽 접속 지연, 이미 접속한 정상 채널의 메시지 지연, 빈 채널 재시도를 각각 다른 결론으로 판정한다.
- 같은 연결의 간섭이 확인돼도 서버 소켓 프로세스의 내부 대기를 직접 봤다고 쓰지 않는다. 운영 서버 버전·설정이 없으면 `join_error()`나 Muster를 운영 환경의 확정 원인으로 명시하지 않는다.
- 기존 [기제 보고서](./realtime-delay-mechanism-report.md)의 “빈 토픽 핸들러는 아무것도 기다리지 않는다”는 서술은 `join_error()` 내부 확인 결과와 충돌한다. 측정 결과를 반영한 후속 보고서에서 이를 정정하되, 기존 원본은 보존한다.
