# ADR 0003. 리팩토링 기간의 테스트는 불변식만 엄격하게 고정한다

- 상태: 채택
- 작성일: 2026-11-18
- 결정일: 2026-11-20
- 관련 이슈: [#242](https://github.com/andbread/Andbread_Frontend/issues/242)
- 관련 ADR: [ADR 0001](0001-supabase-data-access-via-route-handlers.md), [ADR 0002](0002-server-state-management-with-react-query.md)

## 한 문장 요약

Route API 이관과 React Query 도입 기간에는 금액, 권한, 데이터 정합성 같은 불변식만 테스트로 엄격하게 고정하고, 문구와 화면 구조는 느슨하게 검증해 화면 정책 변경이 테스트에 막히지 않게 한다.

## 맥락

- ADR 0001과 0002는 겉으로 보이는 동작을 유지한 채 데이터 경로만 바꾸는 작업이다. 동작이 그대로인지 확인할 안전망이 필요하다.
- 1인 개발 환경이고 화면과 화면 정책이 자주 바뀐다. 이전 프로젝트에서는 테스트를 촘촘하게 운영하자 테스트 수정이 변경 속도를 늦추는 병목이 되었다.
- 기존 E2E 51건 중 그룹과 초대 spec은 문구와 화면 구조에 강하게 묶여 있다. 토스트 문구를 그대로 비교하는 assertion이 17곳 있다. 정산 spec은 testid를 거쳐 비교적 안정적이다.
- E2E의 일부 mock이 Supabase 경로(`/rest/v1/...`)를 가로채고 있어, 이관 후에는 요청을 잡지 못한다.

## 결정

### 1. 무엇을 고정하는가

- 금액 계산, 납부 상태, 권한 경계, 서비스 진입 경로 같은 불변식만 엄격하게 검증한다.
- 성공 여부는 화면 문구보다 도착 URL과 DB 상태로 판정한다.
- 토스트 문구 검증은 실패를 알려주는 신호가 토스트뿐인 곳에만 남긴다.

### 2. 테스트 층

| 층 | 대상 | 원칙 |
|---|---|---|
| E2E | P0 여정과 일부 P1 | 리팩토링의 기준선으로 쓴다 |
| Route Handler 통합 | 공통 인증 래퍼, 쓰기와 권한이 걸린 엔드포인트 | 이관 PR과 함께 추가한다 |
| 단위 | 순수 계산과 판정 | 로직을 떼어낼 때 추가한다 |

- 컴포넌트 테스트, MSW, lib 함수 mock 테스트는 도입하지 않는다.
- 실제 테스트용 Supabase와 기존 `e2e/fixtures`의 seed를 그대로 쓴다.
- 커버리지 목표는 두지 않는다.

### 3. PR 운영

- 리팩토링 PR과 기획 변경 PR을 섞지 않는다.
- 리팩토링 PR에서 테스트가 깨지면 코드를 먼저 의심한다. 테스트를 고쳤다면 PR의 Review Points에 이유를 적는다.
- 기획 변경 PR에서는 테스트를 자유롭게 고치거나 지운다.
- 테스트 PR은 해당 도메인에 P0 케이스가 비어 있을 때만 리팩토링 PR보다 먼저 올린다.
- 이관 PR에서는 해당 도메인의 E2E mock 경로를 `/api/*`로 옮기고, mock이 실제로 요청을 잡는지 확인한다.

### 4. 테스트의 수명

- 기획 변경으로 깨진 테스트가 P0 불변식을 검증하지 않으면 고치지 않고 지운다.
- 리팩토링 안전망으로 추가한 테스트는 이관이 끝난 뒤 다시 평가해 정리할 수 있다.
- 부가 도메인(친구, 채팅, 게시글, 알림)은 자동 테스트를 추가하지 않고 PR의 수동 확인 항목으로 대신한다.

### 5. 테스트 명세 관리

- Notion `테스트 시나리오` DB는 지금처럼 전체 케이스를 관리하고, 개발하면서 코드와 계속 동기화한다.
- E2E 외 테스트(Route Handler 통합, 단위)도 이 DB에 명세한다.
- 코드에서 테스트를 지우면 Notion row도 함께 지운다.

### 6. 머지 기준

- typecheck, lint, 단위 테스트, 통합 테스트, E2E(mobile)를 통과해야 한다.
- 리팩토링 대상 도메인에서 flaky 테스트가 나오면 merge를 미룬다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 리팩토링 PR에서 테스트 수정을 전면 금지 | 리팩토링 기간에도 화면 정책은 바뀐다. 규칙을 지키려면 기획 변경을 미루거나 규칙을 어겨야 한다. |
| 도메인마다 테스트 PR을 항상 먼저 올림 | 1인 개발에서 PR 수가 두 배가 된다. |
| 엔드포인트마다 통합 테스트 3종 작성 | 100건이 넘는다. 인증과 토큰 격리는 공통 래퍼 한 곳에서 검증하면 충분하다. |
| 부가 도메인에 스모크 E2E 추가 | 화면이 가장 자주 바뀌는 영역이라 유지 비용이 효과보다 크다. |
| Notion은 P0만 관리하고 나머지는 코드를 원본으로 삼음 | 테스트 케이스를 Notion에서 직접 관리할 때 명세가 더 명확하다. |
| 컴포넌트 테스트나 MSW 도입 | 리팩토링하면 함께 바뀌는 층이라 안전망이 되지 못하고, mock은 RLS를 검증할 수 없다. |

## 결과

### 좋아지는 것

- 화면 문구나 구조가 바뀌어도 불변식이 같으면 테스트가 깨지지 않는다.
- 테스트를 고칠지 지울지의 판단 기준이 생겨, 깨진 테스트를 두고 고민하는 시간이 줄어든다.
- 리팩토링 PR에서 테스트가 깨지면 코드 문제일 가능성이 높아 원인을 빠르게 좁힐 수 있다.

### 비용과 위험

- 그룹과 초대 spec의 문구 기반 assertion을 URL과 DB 상태 기반으로 바꾸는 작업이 먼저 필요하다.
- 문구와 화면 구조의 회귀는 자동으로 잡지 못하고 수동 확인에 의존한다.
- "P0 불변식이 아니면 지운다"는 기준을 느슨하게 적용하면 안전망이 조금씩 얇아질 수 있다.
- 이 기준으로 P1 E2E 13건을 지우면서 중복 초대 방지(INVITE-SEND-001), 그룹 삭제 시 DB 삭제(GROUP-DELETE-001), 거절한 초대의 재수락 불가(INVITE-RESPOND-004) 검증이 E2E에서 빠졌다. Route Handler 통합 테스트에서 다시 다룰지 정해야 한다.

## 확인 필요

- 화면 간 동기화 E2E를 "납부 변경 후 홈 합계" 1건으로 충분하다고 볼지
- 통합 테스트를 Vitest의 별도 project로 두는 방식과 CI에서 테스트 DB 접속 정보를 받는 위치
- 그룹과 초대 spec의 assertion 정리를 리팩토링 전에 할지, 해당 도메인을 이관할 때 함께 할지
