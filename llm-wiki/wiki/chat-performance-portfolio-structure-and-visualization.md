# 채팅 성능 개선 포트폴리오의 분할 기준과 시각화 설계

## 한 문장 요약

채팅 성능 개선을 포트폴리오 두 편으로 나눌 때는 **기다리는 시간을 줄인 개선과 일하는 시간을 줄인 개선으로 가르고, 두 편이 같은 성과 수치를 쓰지 않도록 끊어야 한다.**

## 확인된 내용

### 두 편을 가르는 기준은 지표다

항목별 측정 결과, 개선 항목이 **영향을 주는 지표가 완전히 갈렸다.** 체감 지연을 줄인 항목은 렌더를 거의 건드리지 않았고, 렌더를 99% 줄인 항목은 체감 지연을 한 자릿수 밀리초도 줄이지 못했다.

| 개선 항목 | 체감 지연 | 렌더 비용 |
| --- | --- | --- |
| 낙관적 업데이트 | −3732.1ms (p<0.001) | 해석 보류 |
| Realtime 구독 정상화 | −2976.8ms (p<0.001) | 없음 (p=0.402) |
| 컴포넌트 분리와 메모이제이션 | 없음 (p=0.871) | −904.8ms (p<0.001) |
| 시간 포맷 사전 계산 | 없음 (p=0.685) | −872.9ms (p<0.001) |
| 스크롤 처리 교체 | 검출 한계 미만 | −340.4ms (p<0.001) |

따라서 포트폴리오도 이 선을 따라 나누는 것이 자연스럽다.

### 성과 수치가 겹치지 않게 끊어야 한다

| | 1편 (구독 정상화 + 낙관적 업데이트) | 2편 (분리·메모이제이션) |
| --- | --- | --- |
| 대표 수치 | 전송 지연 **3984ms → 252ms** | 렌더 비용 **914ms → 5.2ms** |
| 보조 수치 | 수신 이벤트 도착 4219ms → 520ms | 체감 지연 252ms → **51ms** |

**최종 51ms를 1편에 쓰면 안 된다.** 거기까지 도달하려면 2편의 개선이 필요하기 때문이다. 2편이 1편이 끝난 252ms 지점을 이어받는 구조로 쓰면 두 편이 중복 없이 연결된다.

### 두 편의 문제 인식은 달라야 한다

1편은 **사용자가 이미 겪고 있던 결함**이다. 메시지를 보내면 3~4초 뒤에야 화면에 나타났다.

2편은 그렇지 않다. **타이핑 지연은 실사용에서 체감되지 않았다.** CPU 제한을 풀고 환산하면 메시지 100건에서 한 글자당 약 46ms인데, 사람이 입력 지연을 느끼는 기준인 100ms 아래다. 따라서 2편의 문제 인식은 두 가지로 잡아야 한다.

첫째는 **확장성**이다. 한 글자 칠 때마다 목록 전체가 다시 그려져 비용이 메시지 수에 비례해 늘어나는 구조였다. 메시지가 쌓이면 터진다.

둘째는 **기다림을 없앤 뒤 드러난 병목**이다. 1편이 끝난 252ms 중 약 200ms가 렌더 비용이었다.

### 1편에 쓸 시각화

**워터폴 차트(필수).** 개선 전 3984ms에서 구독 정상화로 1007ms, 낙관적 업데이트로 252ms에 이르는 두 단계를 계단으로 그린다. 두 감소분에 같은 색 계열을 써서 **둘 다 기다리는 시간이었다**는 메시지를 전달한다.

**3조건 비교 막대(필수).** 개선 전 4219ms, 개선 전에 가드 한 줄만 추가 520ms, 개선 후 536ms를 나란히 놓는다. 가운데 막대에 `if (!nbreadId) return`을 코드로 표기하면 **한 줄만 다른 버전으로 원인을 확정했다**는 설계 과정이 그림 하나로 전달된다. 수신 경로 실험이므로 별도 측정임을 캡션에 밝힌다.

**조건 무관성 막대(선택).** 개선 전 전송 지연이 지연 없음 3961ms, 왕복 +400ms 3890ms, 300건 3750ms로 거의 같은 높이인 그림이다. 네트워크를 느리게 해도 메시지를 3배로 늘려도 변하지 않았다는 것이 원인 추적의 출발점이었으므로, 서사가 있는 자료가 된다.

### 2편에 쓸 시각화

**확장성 선그래프(필수).** 가로축 메시지 수, 세로축 10자 입력 시 렌더 비용으로 선 두 개를 그린다. 개선 전은 1844ms에서 5372ms로 2.91배 증가하고, 개선 후는 9.9ms에서 11.2ms로 1.14배에 그친다. **기울기 차이가 이 그림의 전부**이며, 비용이 메시지 수와 무관해졌다는 것이 숫자 없이도 보인다.

**커밋당 렌더 비용 막대(필수).** 개선 전 226.8ms, 시간 포맷 사전 계산 14.3ms, 분리와 메모이제이션 3.8ms의 세 막대다. 한 번 그릴 때의 비용이 얼마나 싸졌는지를 보여주면서, 두 가지 방법으로 같은 비용을 없앴다는 다음 그림으로 자연스럽게 이어진다.

**중첩 막대(선택, 권장).** 분리·메모이제이션 단독 905ms, 시간 포맷 단독 873ms, 단순 합 1778ms를 점선으로, 실제 동시 적용값 906ms를 실선으로 그린다. **항목별 수치를 더하면 두 배로 부풀려진다**는 것을 그림 하나로 설명할 수 있어, 측정을 제대로 설계했다는 인상을 준다.

### 도식화할 때 지킬 것

**로그 스케일을 쓰지 않는다.** 3984ms와 51ms는 78배 차이라 선형 막대로는 마지막 두 개가 보이지 않는데, 로그로 바꾸면 읽는 사람이 감소 폭을 과소평가한다. 워터폴로 줄어든 양을 그리면 이 문제가 사라진다.

**모든 그림에 측정 조건을 한 줄 넣는다.** `메시지 100건 · CPU 4배 제한 · 조건당 20회 중앙값 · 운영 빌드와 운영 DB` 형태다. 대부분의 성능 개선 사례에는 조건이 없으므로, 이 한 줄이 차별점이 된다.

**p값과 효과 크기는 캡션에 둔다.** 막대 위에 올리면 지저분해진다. "12개 셀 전부 p<0.001, 효과 크기 1.00" 한 줄로 충분하다.

**타이핑 5372ms를 크게 쓰지 않는다.** CPU 4배 제한에 메시지 300건이라는 가혹한 조건의 값이므로, 사용자가 겪은 시간처럼 보이면 과장이 된다. 쓴다면 저사양 기기 가정이라는 표기를 반드시 붙인다.

### 두 편에 공통으로 넣을 문장

> 조건당 20회 반복하고, 조건 순서를 회차마다 교차했으며, 중앙값과 사분위 범위로 보고했습니다. 가설과 판정 기준은 측정 전에 확정했고 기각된 가설도 그대로 실었습니다.

## 확인 필요

- 시각화를 실제로 만들어 본 뒤 워터폴이 읽히는지 검증하지 않았다. 감소 폭이 2977ms, 755ms, 200ms로 편차가 커서 마지막 계단이 너무 작게 보일 수 있다.
- 2편의 "확장성 문제" 서사가 채용 담당자에게 설득력이 있는지는 확인하지 않았다. 이미 발생한 문제를 고친 1편에 비해 약하게 읽힐 여지가 있다.
- 1편의 수신 경로 수치(4219ms → 520ms)와 전송 경로 수치(3984ms → 252ms)는 측정 방식이 달라 같은 축에 놓을 수 없다. 한 편 안에서 두 수치를 어떻게 배치할지는 정하지 않았다.

## 다시 물어볼 질문

- 포트폴리오를 읽는 사람이 측정 조건 표기를 부담스러워하지 않는가. 신뢰도를 높이는 장치가 오히려 장황하게 읽힐 수 있다.
- 2편에서 시간 포맷 사전 계산을 별도 항목으로 다룰 것인가, 아니면 메모이제이션 안에 묶을 것인가. 렌더 비용 기여는 873ms로 거의 대등하다.
