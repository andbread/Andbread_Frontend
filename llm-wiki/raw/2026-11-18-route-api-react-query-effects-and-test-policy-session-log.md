# Route API 이관과 React Query 도입 효과, 리팩토링 테스트 정책 세션 기록

출처: Claude Code 세션 대화
확인 날짜: 2026-11-18

## 세션 목적

프로젝트의 핵심 과제인 route api 이관(#170)과 React Query 도입(#173, #240)을 도메인이나 페이지 단위로 나눠 진행하기 전에 두 가지를 정리했다.

1. 리팩토링 전에 절대 깨지면 안 되는 동작을 테스트로 명세하기 위한 테스트 정책
2. 두 작업으로 구체적으로 무엇이 좋아지고 무엇을 개선할 수 있는지에 대한 키워드 정리

이 기록은 세션에서 제안한 내용을 그대로 보존한다. 확정된 결정이 아니라 제안이며, 결정은 `wiki/adr/`에 따로 남긴다.

## 1부. 리팩토링 테스트 정책 제안

### 정책 1. 리팩토링이 지켜야 할 기준은 E2E가 맡는다

route api 이관과 React Query 도입은 둘 다 겉으로 보이는 동작은 그대로 두고 데이터가 오가는 경로만 바꾸는 작업이다. 그래서 기준이 되는 테스트는 리팩토링하는 동안 바뀌지 않는 층에 있어야 한다.

- E2E(브라우저에서 DB까지)는 리팩토링 전후로 그대로 유지되므로 안전망으로 쓴다.
- lib 함수를 Supabase mock으로 감싼 단위 테스트는 쓰지 않는다. 이관하면 `src/lib/<도메인>/*.ts` 안쪽이 통째로 바뀌어 테스트도 함께 다시 써야 한다.
- 컴포넌트 테스트(RTL, jsdom)는 도입하지 않는다. 설정 비용이 들고, React Query 전환 중 컴포넌트 구조가 바뀌며, E2E가 같은 내용을 검증한다.

### 정책 2. 테스트를 세 층으로 나누고 층마다 맡는 범위를 정한다

| 층 | 도구 | 대상 | 원칙 |
|---|---|---|---|
| E2E | Playwright (기존) | P0/P1 사용자 흐름 | 리팩토링 전에 반드시 통과해야 한다 |
| 단위 | Vitest (기존) | 순수 계산과 판정 | 리팩토링 중 순수 로직을 떼어내면 그때 추가한다 |
| Route Handler 통합 | Vitest (새 project) | 이관한 `app/api` 엔드포인트 | 이관 작업과 함께 추가한다 |

Route Handler 통합 테스트를 두는 이유는 이관 설계서의 핵심 위험이 화면에 드러나지 않기 때문이다. 요청마다 클라이언트를 새로 만들지 않아 다른 사용자 토큰으로 쿼리가 나가는 경우, RLS 적용 여부, 비로그인 접근을 허용하는 유일한 엔드포인트인 `GET /api/invites/[token]`이 여기에 해당한다. 엔드포인트마다 비로그인 401, 본인 데이터 정상, 타인 데이터 거부나 빈 결과 세 건만 검증한다. mock 대신 E2E와 같은 테스트 DB와 seed helper를 쓴다.

### 정책 3. 도메인마다 테스트 PR을 먼저, 리팩토링 PR을 그다음에 올린다

```
① 기준선 확인: 해당 도메인의 P0/P1 케이스가 develop에서 통과하는지 확인
② 테스트 PR: 빠진 케이스를 기존 코드 기준으로 작성해 통과시키고 merge (코드 변경 없음)
③ 리팩토링 PR: 테스트 assertion은 수정하지 않음
```

리팩토링 PR에서 테스트 파일을 고칠 수 있는 범위는 네트워크 mock 경로뿐이다. assertion을 고쳐야 한다면 동작이 바뀌었다는 뜻이므로 PR을 멈춘다. 테스트 diff가 생기면 PR의 Review Points에 이유를 적는다. 테스트 PR을 따로 merge하면 그 테스트가 기존 코드에서 통과했다는 기록이 남는다.

### 정책 4. 테스트가 없는 도메인은 리팩토링 전에 스모크 테스트만 추가한다

친구, 채팅, 게시글, 알림은 도메인마다 1~2건(목록 조회, 대표 쓰기 동작 하나)만 추가한다. 커버리지 목표 %는 정하지 않는다.

### 정책 5. React Query 도입 시 추가로 검증할 항목

- 데이터를 바꾼 뒤 다른 화면으로 이동하면 새로고침 없이 바뀐 값이 보이는지 확인한다 (납부 상태 변경 후 홈 합계, 그룹 생성 후 홈 목록).
- 낙관적 업데이트가 실패하면 원래 상태로 돌아가는지 확인한다 (SETTLE-UPDATE-002).
- 중복 요청이 한 번으로 합쳐지는지 확인한다 (SETTLE-UPDATE-001).

첫 번째 항목을 기존 E2E가 검증하는지는 모든 assertion을 읽어 보지 않아 확인하지 못했다.

### 정책 6. CI와 flaky 기준

- 리팩토링 PR은 단위 테스트와 E2E(mobile)를 모두 통과해야 merge한다.
- 재시도로 통과한 flaky 테스트가 리팩토링 대상 도메인에서 나오면 merge를 미룬다.

### 발견한 위험: E2E mock이 Supabase URL에 묶여 있다

E2E 9곳이 `/rest/v1/...` 경로를 가로챈다 (`e2e/group.spec.ts:165,253`, `e2e/settlement.spec.ts:234,326`, `e2e/invite.spec.ts:293,462`, `e2e/auth.spec.ts:271` 등). 이관 후 브라우저가 `/api/...`를 호출하면 이 mock은 아무 요청도 가로채지 못한다. 실패 경로 테스트는 빨갛게 깨지므로 금방 드러나지만, 요청 횟수를 세는 테스트(SETTLE-UPDATE-001)는 단언 방식에 따라 잘못된 통과가 날 수 있다. 이관 PR마다 mock이 새 경로에서 실제로 요청을 잡는지 확인하기로 제안했다.

### 도메인 진행 순서 제안

1. 정산(nbreadRecord): P0가 가장 많고 #240이 첫 대상으로 잡혀 있다.
2. 그룹(nbread)
3. 초대: 공개 엔드포인트와 RPC가 있어 통합 테스트가 가장 중요하다.
4. 친구, 알림, 채팅, 게시글: 스모크 테스트를 추가한 뒤 진행한다.
5. 인증과 약관: 이관 설계서에서 제외했으므로 쿠키 세션 전환 때 다룬다.

### 채택하지 않은 대안

- MSW로 Supabase를 mock하는 방식은 실제 테스트 DB가 이미 있어 이점이 적고 RLS를 검증할 수 없다.
- 커버리지 기준치는 1인 개발에서 숫자를 맞추는 비용만 늘린다.
- lib 함수를 mock한 단위 테스트는 리팩토링하면 함께 버려진다.

## 2부. Route API와 React Query 도입 효과 (키워드 정리)

### Route API 이관

이관만으로 바로 좋아지는 것

- 데이터 접근 창구 단일화: 브라우저에서 Supabase를 직접 호출하던 39개 함수가 `/api/*`를 거친다.
- 왕복 횟수 감소: `insertParticipant`의 브라우저와 DB 사이 4번 왕복이 1번으로 줄어든다.
- 네트워크 관측 단순화: Sentry 추적과 E2E mock 대상이 `/api/*` 하나로 정리된다.
- 서버에서만 쓸 수 있는 값 처리: service role, 외부 API 키를 쓰는 로직을 둘 자리가 생긴다.

이관 후 개선할 수 있는 것

- 쿠키 세션 전환: `@supabase/ssr`과 middleware를 쓸 수 있다. 지금은 세션이 localStorage에만 있다.
- SSR과 서버 컴포넌트: 첫 화면에 데이터를 담아 내려 로딩 깜빡임을 줄이고 LCP를 개선할 수 있다.
- 접근 제어를 middleware로 이동: `protectRoute`가 경로 변경마다 하던 사용자 조회를 서버에서 판정한다.
- 정원 검사 경쟁 조건 해소: 참여자 삽입을 원자적으로 처리할 자리가 생긴다.
- 에러 처리 규약 통일: `catch`에서 `undefined`를 반환하던 곳을 HTTP 상태 코드와 일관된 에러 형태로 바꿀 수 있다.
- 서버 쪽 입력 검증: `.or()` 문자열 보간 같은 곳에서 입력을 검증할 위치가 생긴다.
- 방어 계층 추가: RLS에 더해 API 단에서 권한을 한 번 더 확인할 수 있다.
- 쿼리 최적화: N+1 제거와 쿼리 통합을 화면 단위 엔드포인트에서 할 수 있다.

### React Query 도입

서버 상태 관리

- zustand와 역할 분리: 서버 데이터는 React Query, UI 상태는 zustand가 맡는다.
- 로딩과 에러 상태 표준화: `useEffect` + `useState` 패턴을 걷어낸다.
- 캐싱: 탭 이동과 뒤로 가기에서 같은 데이터를 다시 요청하지 않는다.
- 중복 요청 제거: 여러 컴포넌트가 같은 데이터를 요청해도 한 번만 보낸다.

정산 화면에 직접 쓰이는 기능

- 낙관적 업데이트와 롤백: #241, SETTLE-UPDATE-002
- 실패 후 재시도: 세션에서는 #237을 `retry`와 mutation 상태로 해결할 수 있다고 정리했다. (아래 정정 메모 참고)
- 연속 클릭 처리: `isPending` 상태로 수동 스로틀을 대체한다.
- 변경 후 다른 화면 동기화: `invalidateQueries`로 홈 합계를 갱신한다.

체감 성능과 사용자 경험

- stale-while-revalidate: 캐시된 화면을 먼저 보여주고 뒤에서 새 데이터를 받는다.
- 창 포커스 시 자동 갱신: 다른 참여자가 바꾼 납부 상태가 반영된다.
- 미리 불러오기: 홈 그룹 카드 시점에 상세 데이터를 미리 받는다.
- SSR과 함께 쓸 때 hydration으로 서버 데이터를 이어서 쓴다.

### 둘을 함께 할 때 생기는 효과

- 엔드포인트 하나에 query 함수 하나가 대응하고, query key 체계가 도메인 구조를 따른다.
- 계층이 `app/api` → `lib/<도메인>` → `hooks/use<도메인>Query` → 컴포넌트 순서로 정리된다.
- API는 통합 테스트로, 화면은 E2E로 테스트 경계가 명확해진다.

### 비용과 주의점

- 지연 시간 증가 가능: 브라우저 → Vercel → Supabase로 한 번 더 거친다. `protectRoute`의 사용자 조회 경로에서 체감될 수 있다.
- Vercel 함수 호출 비용 증가
- 인증 토큰 처리 위험: 요청마다 클라이언트를 새로 만들지 않으면 다른 사용자 토큰이 섞인다.
- 캐시 무효화 누락: 오래된 데이터가 화면에 남는 회귀가 생긴다.
- 실시간 채팅 예외: Realtime 구독은 브라우저 클라이언트에 남는다.

이관 설계서상 route api 작업은 순수 이동이므로 바로 체감되는 개선은 적고, 대부분의 효과는 이후 작업(쿠키 세션, SSR, React Query)에서 나온다.

## 정정 메모

원본 대화 내용은 위에 그대로 두고, 이 기록을 정리하며 확인한 오류를 따로 적는다.

- #237의 "납부 상태 저장 실패 후 재시도 불가" 문제는 React Query 없이 #238에서 잠금을 요청 기준으로 바꾸는 방식으로 이미 고쳤다. #240 본문이 이 사실을 적고 있다. React Query가 맡는 범위는 #241의 연속 클릭 요청 통합과 낙관적 업데이트다.
- #240은 React Query 기본 옵션(실패 시 3회 재시도, 창 포커스 시 재조회)을 그대로 쓰면 E2E에서 요청 횟수와 실패 시나리오가 예상과 달라진다고 지적한다. 세션의 "창 포커스 시 자동 갱신" 항목은 이 옵션 결정과 함께 봐야 한다.
