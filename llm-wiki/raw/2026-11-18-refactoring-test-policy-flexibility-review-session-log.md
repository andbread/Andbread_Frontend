# 리팩토링 테스트 정책의 유연성 검토 세션 기록

출처: Claude Code 세션 대화
확인 날짜: 2026-11-18
이전 기록: `raw/2026-11-18-route-api-react-query-effects-and-test-policy-session-log.md`

## 사용자 문제 제기

최근 다른 프로젝트에서 기존 테스트 문서와 코드를 기준으로 촘촘하게 테스트를 운영해 보니, 변경이 잦고 화면과 화면 정책이 자주 바뀌는 환경에서는 테스트가 오히려 병목이 되었다. 그래서 이번에는 유연한 테스트 정책이 중요하다고 보고, 앞서 제안한 정책이 이 측면에서 문제가 없는지 검토를 요청했다.

## 기존 E2E의 화면 결합도 조사 결과

| spec | getByText | getByRole | getByPlaceholder | testid | toHaveURL |
|---|---|---|---|---|---|
| `auth.spec.ts` | 2 | 8 | 0 | 3 | 13 |
| `group.spec.ts` | 10 | 17 | 6 | 0 | 12 |
| `invite.spec.ts` | 18 | 34 | 2 | 1 | 9 |
| `landing.spec.ts` | 0 | 2 | 0 | 0 | 0 |
| `settlement.spec.ts` | 0 | 0 | 0 | 0 | 0 |

- 토스트 문구를 그대로 비교하는 assertion이 17곳 있다.
- 홈 화면은 `'나의 엔빵'`, `'이번 달 엔빵'` 제목과 `section` 구조로 요소를 짚는다 (`e2e/fixtures/ui.ts`).
- 정산 spec은 `fixtures/ui.ts`의 testid를 거쳐 요소를 짚어 화면 변경에 비교적 강하다. 그룹과 초대 spec은 문구 변경에 약하다.

## 기존 제안에서 병목이 될 수 있는 지점

1. 리팩토링 PR의 assertion 수정 금지 규칙이 리팩토링 기간 중의 화면 정책 변경과 충돌한다.
2. E2E가 불변식(금액, 권한, DB 상태)과 표현(문구, 구조)을 같은 무게로 검증한다.
3. 도메인마다 테스트 PR을 먼저 올리면 1인 개발에서 PR 수가 두 배가 된다.
4. Route Handler 통합 테스트 3종을 엔드포인트마다 쓰면 100건이 넘는다.
5. 화면 간 동기화 E2E는 두 화면에 걸쳐 있어 화면 변경에 가장 약하다.
6. 부가 도메인 스모크 테스트는 화면이 가장 자주 바뀌는 영역이라 비용 대비 효과가 낮다.
7. Notion 케이스 DB를 테스트 코드와 동기화하는 비용이 있다.

## 대안으로 제시한 방향

- 불변식은 엄격하게, 화면은 느슨하게 고정한다. 성공 여부는 도착 URL과 DB 상태로 판정한다.
- 테스트 수정을 막는 대신 리팩토링 PR과 기획 변경 PR을 분리한다.
- 테스트 PR은 해당 도메인에 P0가 비어 있을 때만 따로 올린다.
- 통합 테스트는 공통 인증 래퍼를 한 번, 쓰기와 권한이 걸린 엔드포인트만 개별로 검증한다.
- 화면 간 동기화 E2E는 납부 변경 후 홈 합계 1건만 둔다.
- 부가 도메인은 자동 테스트 대신 수동 확인 체크리스트를 쓴다.
- 기획 변경으로 깨진 테스트가 P0 불변식이 아니면 고치지 않고 지운다.
- Notion은 P0만 관리하고 나머지는 코드를 원본으로 삼는 안을 제시했다. 기존 Test Guide를 바꾸는 결정이라 사용자 판단으로 남겼다.

## 유지하기로 한 것

실제 테스트 DB 사용, Supabase mock 미사용, 커버리지 목표 없음, "사용자가 무엇을 잃는가" 기준의 우선순위, E2E mock 경로(`/rest/v1`) 결합 대응은 그대로 둔다.
