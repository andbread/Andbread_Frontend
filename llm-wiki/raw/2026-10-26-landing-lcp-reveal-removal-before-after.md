# 랜딩 첫 화면 스크롤 연출 제거 전후 LCP 비교

작성일 2026-10-26. GitHub Issue [#234](https://github.com/andbread/Andbread_Frontend/issues/234)의 A 작업(랜딩 첫 화면 `RevealOnScroll` 제거) 전후 측정 결과를 보존한 기록이다. 작업 브랜치는 `hm1n/refactor-94-lcp-lcp-p75-2.5`, 변경 커밋은 `8c16723 refactor: 랜딩 첫 화면의 스크롤 연출 제거`이다.

## 문제

- 랜딩 첫 화면의 제목, 버튼, 히어로 이미지가 모두 `RevealOnScroll`로 감싸져 있었다.
- `RevealOnScroll`은 `opacity-0`으로 렌더링한 뒤, 하이드레이션이 끝나고 IntersectionObserver가 동작해야 `opacity-100`으로 바꾼다.
- Chrome은 86 버전부터 투명도 0인 요소의 페인트를 LCP 후보에서 제외한다. 그래서 히어로 이미지 다운로드가 약 1초에 끝나도 LCP는 JS 실행 이후로 기록됐다.
- 감속 없는 조건에서도 이미지 다운로드는 `0.19s`, LCP는 `1.22s`였다. 회선 속도와 관계없이 약 1초가 늦어지는 구조였다.

## 변경 내용

- `src/app/page.tsx` 첫 section의 `RevealOnScroll` 3개를 같은 구조의 `<div>`로 바꿨다.
- 아래쪽 섹션의 `RevealOnScroll`(20곳)과 컴포넌트 자체는 그대로 두었다.

## 측정 조건

- Playwright, Pixel 7 에뮬레이션, Slow 4G(왕복 지연 150ms, 다운로드 1.6Mbps, 업로드 750Kbps), CPU 4배 감속으로 측정했다.
- 폰트 다운로드를 포함했다. PC에 설치된 Pretendard를 쓰지 않도록 폰트 CSS의 `local()` 소스를 제거했다.
- `/monitoring`(Sentry 터널), GA, Clarity 수집 요청은 차단했다.
- 조건마다 10회 측정해 중앙값을 사용했다. 괄호 안은 최솟값과 최댓값이다.
- Preview는 Vercel 배포 보호가 걸려 있어 Vercel OIDC 토큰 헤더를 Preview 주소 요청에만 붙여 접근했다.

| 페이지 | 지표 | 운영 (개선 전) | Preview (A 적용) |
| --- | --- | --- | --- |
| 랜딩 `/` | LCP | `5.91s` (5.54~6.09) | `1.58s` (1.16~3.27) |
| | FCP | `1.11s` | `1.57s` |
| | 마지막 JS 도착 | `4.23s` | `4.45s` |
| | Pretendard 다운로드 완료 | `14.50s` | `15.28s` |
| | LCP 요소 | IMG(히어로 이미지) | IMG(히어로 이미지) |
| 로그인 `/login` | LCP | `6.97s` (5.28~8.51) | `7.96s` (6.83~9.46) |
| | FCP | `1.15s` | `1.37s` |
| | LCP 요소 | H3 | H3 |

- 랜딩 LCP는 `5.91s`에서 `1.58s`로 줄어 이슈 목표인 `2.5s` 이하를 만족했다.
- 운영에서는 FCP 이후 히어로 이미지가 보이기까지 약 4.8초를 더 기다렸다. Preview에서는 FCP와 거의 같은 시점에 LCP가 기록됐다.
- 10회 중 한 번(`3.27s`)만 튀었고 나머지는 `1.16~1.75s` 사이였다.

| 측정 방식 | 랜딩 LCP (개선 전) | 랜딩 LCP (A 적용) |

## 해석과 주의할 점

- Preview는 운영보다 전반적으로 느리게 나왔다. 이번 변경과 관계없는 로그인 페이지도 Preview에서 약 1초 느렸으므로 측정 환경 차이로 판단했다.
  - 서버 응답 속도는 원인이 아니었다. 감속 없이 6회씩 잰 첫 바이트 시간이 운영과 Preview 모두 40~200ms였고, 둘 다 Vercel 캐시 HIT였다.
  - Preview에는 Vercel 도구 모음 스크립트(`vercel.live`) 요청이 하나 더 있었다. 나머지 요청 구성과 렌더링 차단 리소스는 같았다.
  - Preview 요청마다 인증 헤더가 붙어 업로드 시간이 늘었을 수 있다. 이 두 요인의 실제 영향은 `확인 필요`이다.
- 이 차이는 Preview를 불리하게 만드는 쪽이므로 운영에 배포되면 랜딩 LCP는 `1.58s`보다 낮을 가능성이 높다.
- 로그인 페이지는 운영 측정에서도 `5.28~8.51s`로 흔들렸다. 같은 조건의 이전 측정(`5.25~6.62s`, 중앙값 `5.52s`)보다 폭이 넓었다. 측정한 날의 네트워크 상태 차이로 보이며 A와는 관계없는 페이지이다.
- 로그인 본문은 `LoginRedirectGuard`가 localStorage를 확인하기 전까지 `null`을 반환해서 JS 실행 후에 그려진다. 이 문제는 API route 로그인 이관 후 별도로 다루기로 해서 이번 범위에서 제외했다.
- 이 값들은 실험실 측정의 중앙값이며 Sentry 실제 사용자 p75가 아니다. 릴리즈 후 `environment:production !browser.name:HeadlessChrome` 조건으로 p75를 확인해야 한다.

## 참고 기준값

이슈 분석 단계에서 같은 조건으로 운영을 10회 측정한 값은 랜딩 LCP `6.57s`, 로그인 LCP `5.66s`였다. PageSpeed Insights는 Lantern 시뮬레이션으로 랜딩 LCP를 `16.3s`로 계산해 실측보다 크게 나왔기 때문에 참고용으로만 사용했다.
