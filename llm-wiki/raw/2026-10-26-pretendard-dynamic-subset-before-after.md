# Pretendard dynamic subset 적용 전후 비교

작성일 2026-10-26. GitHub Issue [#234](https://github.com/andbread/Andbread_Frontend/issues/234)의 B 작업(폰트 용량 축소)에서 폰트 로딩 방식을 고른 근거와 전후 측정 결과를 보존한 기록이다. 작업 브랜치는 `hm1n/refactor-94-lcp-lcp-p75-2.5`이고, 이 문서를 작성한 시점에는 변경이 아직 커밋되지 않았다.

## 문제

- `src/app/layout.tsx`가 jsdelivr의 `pretendard.css`를 불러오고 있었다. 이 CSS는 글자를 줄이지 않은 전체 폰트 파일을 굵기마다 하나씩 사용한다.
- 랜딩 페이지는 Regular, Medium, Bold 세 파일(각 약 750KB, 합계 2,285KB)을 받았다. 랜딩 페이지 전체 용량의 81%에 해당한다.
- `font-display: swap`이 설정되어 있어 폰트가 화면 표시를 막지는 않았다. 그러나 폰트와 JS가 같은 회선을 나눠 쓰면서 마지막 JS 도착이 약 `2.7s`에서 `4.2s`로 늦어졌다.
- Slow 4G에서 Pretendard 다운로드가 끝나는 시점은 랜딩 기준 `14.5s`였다. 그동안 글자는 기본 글꼴로 보였다.

## 변경 내용

```diff
- href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard/dist/web/static/pretendard.css"
+ href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/static/pretendard-dynamic-subset.css"
```

- dynamic subset은 굵기마다 전체 글자를 92개 조각으로 나누고 `unicode-range`로 화면에 나온 글자가 든 조각만 받게 한다.
- 기존 주소에는 버전이 없어 최신 버전을 따라갔다. 2026-10-26 기준 최신은 `1.3.9`였고, 버전 없는 주소와 `@v1.3.9` 주소의 CSS 내용이 같은 것을 해시로 확인했다. 그래서 글꼴 모양은 바뀌지 않고, 이후 예고 없이 바뀌는 일도 막는다.
- 글꼴 이름(`'Pretendard'`), 굵기 9종(100~900), `font-display: swap`이 기존과 같아서 `tailwind.config.ts`와 `globals.css`는 수정하지 않았다.

## 방식을 고른 과정

### 후보

| 후보 | 내용 | 결과 |
| --- | --- | --- |
| 고정 서브셋 (`pretendard-subset.css`) | 자주 쓰는 글자만 담은 파일을 굵기마다 하나씩 받는다 | 제외. 서브셋에 없는 희귀 글자가 기본 글꼴로 표시된다 |
| dynamic subset, 저장소 관리 | 조각 파일을 저장소에 넣고 같은 도메인에서 제공한다 | 보류. 굵기 9종이면 828개 파일, 약 10.2MB가 저장소에 추가된다. `next/font/local`로 92개 조각 구성을 옮길 수 있는지는 `확인 필요`이다 |
| dynamic subset, CDN 유지 | jsdelivr 주소만 바꾼다 | **채택** |

### 결정 기준

- 사용자는 그룹 이름이나 채팅처럼 직접 입력한 희귀 글자도 Pretendard로 표시해야 한다고 정했다. 이 기준으로 고정 서브셋이 빠졌다.
- LCP 목표는 A만으로 달성했기 때문에 B는 폰트 용량과 글꼴 적용 시간만 개선하면 된다. 그래서 변경 범위가 가장 작은 CDN 유지 방식을 골랐다.
- 저장소 관리 방식의 장점(외부 의존 제거, jsdelivr 연결 비용 제거)은 이번에 얻지 않기로 했다. 연결 비용 제거로 줄어드는 시간은 측정하지 않았다.

### dynamic subset 파일 크기

jsdelivr의 `v1.3.9` 조각 파일 크기를 HEAD 요청으로 합산한 값이다.

| 굵기 | 조각 수 | 합계 |
| --- | --- | --- |
| 100~900 각각 | 92개 | 약 1,107~1,147KB |
| 9종 전체 | 828개 | 약 10,232KB |

굵기 하나의 조각을 모두 합치면 기존 전체 파일(약 750KB)보다 크다. 다만 한 사용자가 거의 모든 조각을 받는 경우는 드물다.

## 측정 조건

- Playwright, Pixel 7 에뮬레이션, Slow 4G(왕복 지연 150ms, 다운로드 1.6Mbps, 업로드 750Kbps), CPU 4배 감속으로 측정했다.
- 운영 사이트(`https://www.nbread.co.kr`)에서 브라우저가 받는 `pretendard.css` 응답만 후보 CSS로 바꿔 넣었다. 저장소 코드는 바꾸지 않은 시뮬레이션이다.
- 바꿔 넣은 CSS 응답은 회선 감속을 받지 않으므로 `왕복 150ms + 압축 크기 / 200KB/s`만큼 기다린 뒤 넘겼다.
- PC에 설치된 Pretendard를 쓰지 않도록 `local()` 소스를 제거했다.
- "A 적용" 열은 첫 section의 `.reveal-on-scroll` 투명도를 CSS로 풀어 A를 고친 상태를 흉내 낸 값이다.
- `/monitoring`(Sentry 터널), GA, Clarity 수집 요청은 차단했다.
- 조건마다 10회 측정해 중앙값을 사용했다.

## 결과 1. 현재 방식과 dynamic subset 비교 (시뮬레이션)

| 지표 | 현재 (`pretendard.css`) | dynamic subset | 차이 |
| --- | --- | --- | --- |
| 폰트 CSS 크기(br 압축) | `0.4KB` | `13.5KB` | 증가 |
| 랜딩 폰트 요청 | 3개, `2,285KB` | 33개, `388KB` | 용량 약 83% 감소 |
| 랜딩 Pretendard 다운로드 완료 | `14.52s` | `4.13s` | 약 10.4초 단축 |

| 랜딩 LCP (A 적용 상태) | `1.10s` (1.07~1.16) | `1.20s` (1.10~1.39) | 약 0.1초 증가 |
| 랜딩 마지막 JS 도착 (A 적용 상태) | `4.22s` | `4.68s` | 증가 |

## 결과 2. 로컬 프로덕션 빌드 확인

변경을 적용한 코드를 Sentry DSN을 비우고 빌드해 포트 3100에서 Slow 4G로 열어 확인했다. 폰트 CSS는 `local()` 제거를 위해 Playwright가 대신 받아 넘겼으므로 CSS 전송에는 회선 감속이 걸리지 않았다.

| 항목 | 랜딩 `/` | 로그인 `/login` |
| --- | --- | --- |
| 폰트 요청 | 33개, `389KB` | 14개, `174KB` |
| 적용된 글꼴 | `Pretendard, sans-serif` | `Pretendard, sans-serif` |
| 받은 조각 (굵기별) | 400: 17개, 500: 5개, 700: 15개 | 400: 9개, 500: 5개, 700: 5개 |
| 희귀 글자(똠, 햏, 뷁, 쀍) 추가 시 | 조각 4개 추가, Pretendard로 표시 | 조각 5개 추가, Pretendard로 표시 |

- 랜딩 폰트 용량은 시뮬레이션 값과 같게 나왔다.
- `document.fonts.check('16px Pretendard', '똠햏뷁쀍')`가 `true`를 반환해 희귀 글자 조건을 만족했다.
- lint, 타입 검사, 빌드는 통과했다. lint 경고는 이번 변경과 관계없는 기존 파일에서 나왔다.

## 해석과 주의할 점

- B로 좋아지는 지표는 첫 방문 폰트 용량, 느린 회선에서 Pretendard가 적용되는 시간, 로그인 LCP이다.
- 랜딩 LCP는 A 적용 상태에서 약 0.1초 늘었다. 폰트 CSS가 렌더링을 막는 CSS인데 0.4KB에서 13.5KB로 커졌기 때문으로 본다. `2.5s` 목표에는 영향이 없지만 이슈 완료 조건("B 적용 후 랜딩 LCP가 A 적용 후보다 나빠지지 않았는지 확인")에 해당하므로 Preview에서 다시 확인해야 한다.
- 랜딩 마지막 JS 도착은 dynamic subset에서 오히려 늦어졌고, 로그인은 빨라졌다. 랜딩은 받는 조각 수(33개)가 많아 요청 경합이 생겼을 가능성이 있다. 원인은 `확인 필요`이다.
- dynamic subset은 조각이 도착하는 순서대로 글꼴이 바뀌므로 잠깐 한 문장 안에서 글꼴이 섞여 보일 수 있다. 로컬 확인에서 1.5초, 2.5초, 3.5초 화면을 찍었을 때는 이미 모두 Pretendard로 바뀐 상태라 이 현상을 잡지 못했다. CSS 전송에 감속이 걸리지 않은 영향일 수 있어 Preview에서 다시 봐야 한다.
- 페이지를 연 뒤 새로 나오는 글자(채팅 메시지 등)는 해당 조각을 받는 동안 잠깐 기본 글꼴로 보일 수 있다. 채팅 화면은 로그인이 필요해 확인하지 못했다.
- 외부 서비스 의존(jsdelivr 장애 시 첫 화면 지연), jsdelivr 별도 연결 비용, 방문자 IP의 외부 전달은 기존과 같이 남는다.
- 빠른 LTE나 Wi-Fi에서는 기존 방식도 폰트를 1초 안팎에 받으므로 체감 차이는 주로 느린 회선의 첫 방문자에게 생긴다. 데이터 사용량 감소는 회선과 관계없이 모든 첫 방문자에게 해당한다.

## 남은 확인

- Preview 배포에서 랜딩 LCP, 로그인 LCP, 폰트 용량, Pretendard 다운로드 완료 시간을 같은 조건으로 측정해야 한다.
- Preview에서 글꼴이 조각 단위로 섞여 보이는지 랜딩, 로그인, 채팅 화면을 눈으로 확인해야 한다.
- E2E 테스트는 아직 실행하지 않았다.
