# 실시간 구독 정상화와 낙관적 업데이트로 채팅 전송 지연 개선

> 포트폴리오 1편 v2입니다. 기존 포트폴리오 페이지 양식(문제 인식 / 해결 과정 / 결과, 불릿 서술)에 맞춰 다시 정리했습니다. 서술형 초안은 [v1 문서](./2026-09-23-portfolio-1-chat-send-latency.md)에 있습니다.

---

## 문제 인식

- 채팅방에서 메시지를 보낸 뒤 화면에 반영되기까지 **3~4초**가 걸려, 전송이 실패한 것처럼 보이는 문제 확인
- 네트워크 왕복 지연을 400ms 추가하거나 메시지를 3배로 늘려도 값이 3.8~4.0초에서 변하지 않아, 네트워크와 렌더 비용이 원인이 아님을 확인
- 낙관적 업데이트가 개입할 수 없는 **상대 메시지 수신 경로에서도 동일한 규모의 지연**이 발생해, 실시간 이벤트를 받는 구간의 문제로 범위를 좁힘

## 해결 과정

> **[그림 1] 워터폴 차트** — 3,984ms → 1,007ms → 252ms 두 단계. 두 감소분을 같은 색 계열로 칠해 둘 다 "기다리는 시간"이었음을 드러냄

- 라우트 파라미터를 상태에 복사하는 구조 탓에 첫 렌더에서 `nbreadId`가 빈 문자열이 되고, `supabase.channel('')`로 접속을 시도해 서버가 `TopicNameRequired`로 거절한 뒤 재접속을 반복하는 것을 WebSocket 프레임에서 확인
- `nbreadId`를 `useMemo`로 라우트에서 직접 유도해 빈 문자열 구간을 제거하고, `useEffect`에 넘긴 async 함수를 걷어내 채널 정리 함수가 정상 반환되도록 수정
- 구독을 고쳐도 서버 저장 응답을 기다리는 시간은 남으므로, 전송 즉시 임시 메시지를 그리고 저장 완료 시 실제 메시지로 교체하는 낙관적 업데이트를 적용
- 개선 전 코드에 `if (!nbreadId) return` **한 줄만 추가한 조건을 별도로 빌드**해, 이벤트 도착이 4,219ms → 520ms로 개선 후(536ms) 수준이 되는 것을 확인하고 원인 확정

## 결과

- 전송 체감 지연 **3,984ms → 252ms로 93.7% 감소** (운영 빌드·운영 DB, CPU 4배 제한, 메시지 100건, 조건당 20회 중앙값)
- 단계별로는 구독 정상화가 **−2,977ms**, 낙관적 업데이트가 **−755ms**를 차지했고 두 항목 모두 p < 0.001, 효과 크기 1.00
- 상대 메시지 수신 경로에서도 이벤트 도착 **4,219ms → 520ms로 87.7% 감소**
- 지연의 정체가 연산량인지 대기 시간인지 먼저 구분해야 하며, 원인을 특정하려면 **한 군데만 다른 조건을 만들어 비교**해야 한다는 것을 배움

## 작성 메모 (페이지에는 넣지 않음)

**분량**: 샘플 페이지와 같은 3·4·4 불릿 구성입니다. 한 페이지에 들어가며, 그림 1을 해결 과정 맨 위에 둡니다.

**2편과 겹치지 않게 끊은 지점**: 최종 51ms는 렌더 개선까지 들어가야 나오는 값이므로 이 페이지에서는 **252ms에서 멈춥니다.** 2편이 252ms를 이어받습니다.

**넣지 않은 것**: 처음에는 렌더 성능을 의심해 컴포넌트 분리와 메모이제이션을 함께 적용했으나 이 4초에 대한 기여는 검출되지 않았다는 사실입니다. 정직한 서술이지만 2편의 주제를 미리 깎아내리게 되어 뺐습니다. **면접에서 물어보면 말할 거리로 남겨 두는 편이 낫습니다.**

**대안 그림**: 워터폴 대신 3조건 비교 막대(4,219 / 520 / 536ms)를 쓸 수도 있습니다. 가운데 막대에 가드 한 줄을 코드로 표기하면 원인 확정 과정이 그림 하나로 전달되므로, 설계 역량을 강조하고 싶다면 이쪽입니다.
