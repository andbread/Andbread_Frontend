## 💬 지난 글에는 세 가지 한계가 있었습니다

엔빵은 제가 운영 중인 구독 공유 정산 서비스입니다. 지난 글에서는 이 서비스의 채팅방에서 메시지를 보낸 뒤 화면에 반영되기까지 3초에서 4초가 걸리던 문제를 다뤘고, 컴포넌트를 분리하고 메모이제이션을 적용해 개선한 과정을 정리했습니다.

글을 쓰고 나서 다시 읽어보니 근거로 삼기에는 약한 부분이 눈에 띄었습니다. 정리하면 세 가지였습니다.

첫째, 운영 환경에서 검증하지 못했습니다. React DevTools의 Profiler는 개발 빌드에 붙이기가 쉬운 반면 운영 빌드에서는 그렇지 않아서, 개발 서버에서 측정한 값을 그대로 실었습니다. 개발 빌드는 번들 구성이 다르고 StrictMode가 렌더를 두 번 실행하기 때문에 값이 실제보다 부풀려집니다.

둘째, 측정 환경을 기록하지 않았습니다. 어떤 기기에서, CPU를 얼마나 제한하고, 메시지가 몇 개 쌓인 상태에서 쟀는지를 남기지 않았으므로 누구도 같은 조건을 재현할 수 없었습니다.

셋째, 측정 횟수가 적었습니다. 개선 전과 후의 스크린샷 한두 장이 사실상 결론이었기 때문에, 그 값이 평균에 가까운지 운 좋게 잘 나온 회차인지 구분할 방법이 없었습니다.

그래서 이 세 가지를 보완하는 것을 목표로 처음부터 다시 측정했습니다.

## 🧪 측정 환경을 먼저 못 박았습니다

이번에는 측정을 시작하기 전에 조건을 문서로 고정하고, 빈칸이 남으면 측정을 시작하지 않기로 정했습니다.

| 항목 | 값 |
| --- | --- |
| 기기 | Intel Core Ultra 9 185H (16코어 / 22스레드), RAM 31.5GB |
| OS | Windows 11 Pro 26200 |
| 앱 빌드 | `next build --profile` 후 `next start` (`NODE_ENV=production`) |
| 백엔드 | 운영 Supabase 프로젝트 |
| CPU 스로틀링 | 4배 제한 (모바일 기기 근사) |
| 네트워크 | 제한 없음(N1) / 왕복 지연 400ms 추가(N2) |
| 브라우저 | Chrome Headless Shell 149 |
| 메시지 규모 | 100건 / 300건 |

운영 환경 검증이라는 첫 번째 한계는 `next build --profile`로 풀었습니다. Next.js의 이 옵션은 운영 빌드를 만들면서도 React의 프로파일링 기능을 남겨 두므로, 운영과 같은 번들에서 렌더 시간을 잴 수 있습니다. 백엔드도 개발용이 아닌 운영 Supabase에 그대로 연결했습니다.

여기서 하마터면 놓칠 뻔한 함정이 하나 있었습니다. 저장소의 `.env.local`은 개발 Supabase를, `.env`는 운영 Supabase를 가리키는데, Next.js는 `.env.local`을 더 우선해서 읽습니다. 그대로 두었다면 운영 환경에서 측정했다고 써 놓고 실제로는 개발 프로젝트에 붙은 채로 재고 있었을 것입니다. 우선순위가 가장 높은 `.env.production.local`에 운영 값을 넣고, 측정 시작 시점에 앱이 실제로 접속한 프로젝트를 기록해 확인했습니다.

CPU를 4배로 제한한 이유는 개발용 노트북의 성능이 실제 사용자 기기보다 훨씬 좋기 때문입니다. 제 기기에서 빠르게 나오는 값은 사용자가 겪는 경험을 대변하지 못합니다.

## ⚙️ 개선 전 코드를 다시 만드는 방법

개선 전과 후를 비교하려면 두 버전이 모두 필요합니다. 가장 단순한 방법은 PR을 머지하기 직전 커밋을 그대로 체크아웃하는 것이지만, 이 방법은 쓰지 않았습니다.

PR #144을 머지한 시점은 2026년 5월이고 지금은 8월입니다. 그 사이에 Next.js와 React 버전이 올라갔고 라우팅 구조와 공통 컴포넌트도 바뀌었습니다. 과거 커밋을 통째로 가져오면 채팅과 무관한 3개월치 변경이 전부 섞여 들어오므로, 성능 차이가 무엇 때문에 생겼는지 귀속시킬 수 없습니다.

그래서 현재 코드에 **PR #144의 diff만 거꾸로 적용**해 개선 전 버전을 만들었습니다. 이렇게 하면 두 버전의 차이가 이 PR이 바꾼 7개 파일로 한정됩니다.

```bash
git diff 1760083 a1c2050 -- \
  src/components/chat src/lib/chatMessage \
  src/types/chatMessage.ts src/utils/formatChatMessageTime.ts > pr144.patch

git apply -R pr144.patch
```

계측 코드도 같은 원칙으로 넣었습니다. React의 `<Profiler>` 컴포넌트는 감싼 영역의 렌더 시간을 콜백으로 알려주는데, 이 래퍼를 **PR #144이 건드리지 않은 파일**인 `src/app/nbread/[nbreadId]/page.tsx`의 `<ChatRoom />` 호출부에만 넣었습니다. 두 버전의 계측 파일이 바이트 단위로 같다는 것도 확인했습니다. 계측이 한쪽에만 유리하게 들어가면 비교 자체가 무의미해지기 때문입니다.

여기서 한 가지 분명히 해 둘 것이 있습니다. **이번 재측정에는 React DevTools를 쓰지 않았습니다.** 지난 글에서는 DevTools의 Profiler 패널을 열어 화면을 보며 병목을 찾았지만, 이번에는 React가 제공하는 `<Profiler>` 컴포넌트의 `onRender` 콜백을 코드로 수집했습니다. 두 방법이 읽는 데이터는 같은 React 프로파일링 정보이지만 도구가 다르므로, 지난 글의 캡처와 이번 표의 숫자를 같은 자로 잰 값처럼 나란히 두면 안 됩니다.

DevTools 패널을 쓰지 않은 이유는 반복 측정 때문입니다. 패널은 사람이 화면을 보며 조작하는 도구여서 480회를 돌릴 수 없고, 스크린샷 한 장으로는 분포를 담지 못합니다. 지난 글의 한계 세 번째가 정확히 이 지점이었습니다.

측정은 Playwright로 자동화했습니다. 회차마다 새 브라우저 컨텍스트를 열고, CPU와 네트워크 조건을 걸고, 로그인 세션을 주입한 뒤 채팅 탭으로 바로 진입하도록 했습니다. 그리고 개선 전 20회를 몰아서 돌린 다음 개선 후 20회를 돌리는 대신, **회차마다 순서를 뒤집어 번갈아 실행**했습니다. 기기가 뜨거워지거나 백그라운드 상태가 변하는 영향이 한쪽 조건에만 실리는 것을 막기 위해서입니다.

## 📊 측정 결과

시나리오는 다섯 가지로 나눴습니다. 채팅방 진입(S1), 메시지 1건 전송(S2), 상대 메시지 1건 수신(S3), 입력창에 10자 타이핑(S4), 연속 5건 전송(S5)입니다. 여기에 메시지 규모와 네트워크 조건을 조합해 12개 셀을 만들고, 셀마다 개선 전후로 각각 20회씩 측정했습니다. 워밍업 3회는 버렸고, 최종 데이터는 480행입니다.

### 렌더 비용

`<Profiler>`가 기록한 채팅방 영역의 렌더 시간 합계입니다.

| 시나리오 | 개선 전 | 개선 후 | 감소율 |
| --- | --- | --- | --- |
| 진입 (100건) | 172.4ms | 36.0ms | **79.1%** |
| 진입 (300건) | 362.7ms | 65.6ms | **81.9%** |
| 전송 (100건) | 927.9ms | 5.0ms | **99.5%** |
| 전송 (300건) | 2797.8ms | 6.0ms | **99.8%** |
| 수신 (100건) | 157.6ms | 6.4ms | **96.0%** |
| 타이핑 (100건) | 1844.0ms | 9.9ms | **99.5%** |
| 타이핑 (300건) | 5372.0ms | 11.2ms | **99.8%** |
| 연속 5건 전송 | 4401.5ms | 29.3ms | **99.3%** |

12개 셀 전부에서 p값이 0.001 미만이고 효과 크기는 1.00입니다. 효과 크기 1.00은 개선 전 20회와 개선 후 20회가 값의 범위조차 겹치지 않았다는 뜻입니다.

여기서 눈여겨볼 것은 타이핑 시나리오입니다. 지난 글에서는 다루지 않았는데, 개선 전 코드는 입력창의 상태를 메시지 목록과 같은 컴포넌트에 두고 있어서 **한 글자를 칠 때마다 메시지 전체가 다시 렌더**되었습니다.

| 타이핑 10자 | 100건 | 300건 | 증가 배수 |
| --- | --- | --- | --- |
| 개선 전 | 1844.0ms | 5372.0ms | **2.91배** |
| 개선 후 | 9.9ms | 11.2ms | **1.14배** |

메시지를 3배로 늘렸을 때 개선 전은 비용이 2.91배로 함께 늘어난 반면, 개선 후는 1.14배에 그쳤습니다. 즉 개선 후에는 렌더 비용이 쌓인 메시지 수와 사실상 무관해졌습니다. `React.memo`가 실제로 동작하고 있다는 가장 직접적인 증거입니다.

### 체감 지연

키보드에서 Enter를 누른 순간부터 메시지가 화면에 그려질 때까지 잰 값입니다.

| 시나리오 | 개선 전 | 개선 후 | 감소율 |

| 전송 (100건, 지연 없음) | 3961.0ms | 49.2ms | **98.8%** |
| 전송 (100건, 지연 400ms) | 3890.5ms | 51.8ms | **98.7%** |

## 🔍 예상이 빗나간 지점

측정을 시작하기 전에 가설을 여섯 개 세우고 판정 기준을 미리 정해 두었습니다. 결과를 본 뒤에 유리한 지표만 골라내는 것을 막기 위해서였습니다. 다섯 개는 지지되었고, 하나가 기각되었습니다.

기각된 가설은 "네트워크가 느릴수록 낙관적 업데이트의 효과가 더 크게 나타날 것"이었습니다. 낙관적 업데이트는 서버 응답을 기다리지 않고 화면을 먼저 갱신하는 방식이므로, 왕복 지연이 클수록 이득도 커진다고 예상했습니다. 그러나 왕복 지연을 400ms 추가한 조건에서 감소율은 98.7%로, 지연이 없는 조건의 98.8%와 사실상 같았습니다.

왜 그런지 개선 전의 값을 나란히 놓고 보니 이상한 점이 보였습니다.

| 개선 전 전송 지연 | 값 |
| --- | --- |
| 100건, 지연 없음 | 3961.0ms |
| 100건, 왕복 지연 400ms 추가 | 3890.5ms |
| 300건, 지연 없음 | 3749.6ms |

네트워크를 400ms 느리게 만들어도, 메시지를 3배로 늘려도 값이 **3.8초에서 4.0초 사이에서 거의 변하지 않았습니다.** 네트워크 왕복도 렌더 비용도 이 지연을 설명하지 못한다는 뜻입니다.

결정적인 단서는 상대 메시지 수신 시나리오에 있었습니다. 이 시나리오는 다른 사람이 보낸 메시지를 받는 상황이므로 낙관적 업데이트가 개입할 여지가 전혀 없습니다. 그런데도 **4328.5ms에서 462.3ms로** 큰 차이가 났습니다. 이 중 렌더 비용의 차이는 157.6ms에서 6.4ms, 즉 151ms에 불과했습니다. 나머지 약 3.7초는 Realtime 이벤트가 앱에 도달하는 시간 자체의 차이였습니다.

개선 전 코드를 다시 열어보고 원인으로 의심되는 곳을 찾았습니다.

```js
// 개선 전: nbreadId의 초깃값이 빈 문자열입니다
const [nbreadId, setNbreadId] = useState<string>('')

// async 함수를 호출하므로 cleanup 반환값이 React에 전달되지 않습니다
useEffect(() => { subscribeChatRoom() }, [nbreadId])
```

`nbreadId`가 아직 빈 문자열인 상태에서 구독이 먼저 실행되면서 `supabase.channel('')`로 접속을 시도합니다. 서버는 `TopicNameRequired: You must provide a topic name` 오류로 이 요청을 거절하고, 클라이언트는 이 빈 채널에 접속과 해제를 반복합니다. WebSocket 프레임을 직접 열어보고 확인한 내용입니다. 여기에 더해 `useEffect`에 넘긴 함수가 async이기 때문에 정리 함수가 React에 전달되지 않아, 채널이 해제되지 않고 계속 쌓입니다.

## 🧪 그런데 이 설명에는 구멍이 있었습니다

여기까지 정리해 두고 다시 읽어보니 앞뒤가 맞지 않는 부분이 있었습니다. 빈 문자열로 채널에 접속하는 것은 채팅방에 들어가는 순간에 한 번 일어나는 사건입니다. 그런데 이번 측정은 화면이 다 그려진 뒤에 **5초**를 기다린 다음 메시지를 주고받았습니다. 진입 시점의 한순간이 5초 뒤의 **4초** 지연을 만든다는 설명은 그대로 받아들일 수 없었습니다.

정황은 맞아떨어졌지만 인과를 확인한 것은 아니었습니다. 그래서 의심하는 한 곳만 바꾼 버전을 따로 만들어 세 조건을 비교하기로 했습니다.

| 조건 | 코드 |
| --- | --- |
| A | 개선 전 원본 |
| B | 개선 전 원본에 `if (!nbreadId) { return }` 가드 한 줄만 추가 |
| C | 개선 후 |

B가 이 실험의 핵심입니다. B는 A와 정확히 한 줄만 다르고, 메모이제이션도 낙관적 업데이트도 없는 개선 전 코드 그대로입니다. 따라서 **A와 B의 차이는 전부 빈 채널 구독의 몫**이고, **B와 C의 차이는 나머지 개선의 몫**입니다.

지연을 두 구간으로 쪼개기 위해 앱 코드는 건드리지 않고 브라우저 밖에서 WebSocket 프레임의 도착 시각을 관측했습니다. 여기서 프레임이란 서버가 실시간 통로로 보내는 실제 데이터 조각을 말합니다. 앱을 고치지 않았으므로 세 조건에 같은 계측이 적용됩니다.

### 메시지를 받는 경로: 원인이 확정됐습니다

조건마다 20회씩 재고 중앙값을 냈습니다.

| 조건 | 전체 지연 | 프레임 도착까지 | 도착 후 화면에 보일 때까지 | 렌더 비용 |
| --- | --- | --- | --- | --- |
| A 개선 전 | 4550.0ms | 4219.0ms | 320.0ms | 247.1ms |
| B 가드 한 줄 | **903.0ms** | **520.0ms** | 396.5ms | 260.0ms |
| C 개선 후 | 596.5ms | 536.0ms | 131.0ms | 7.8ms |

가드 한 줄만 넣었더니 이벤트가 도착하는 데 걸리는 시간이 **4219ms에서 520ms로** 떨어져 개선 후인 **536ms**와 사실상 같아졌습니다. `TopicNameRequired` 오류 프레임도 A에서는 회차마다 2건씩 관측되다가 B와 C에서는 한 건도 나오지 않았습니다.

B의 렌더 비용이 **260.0ms**로 A의 **247.1ms**와 같은 수준이라는 점이 이 결과를 뒷받침합니다. B는 렌더 최적화가 전혀 없는 개선 전 코드이므로 렌더 비용은 그대로 남아야 하고, 실제로 그랬습니다. 줄어든 시간은 렌더가 아니라 이벤트가 오는 구간에서 나왔습니다.

### 메시지를 보내는 경로: 원인이 절반씩이었습니다

같은 방식으로 전송 경로도 재 보았습니다.

| 조건 | 전체 지연 | 프레임 도착까지 | 도착 후 화면에 보일 때까지 |
| --- | --- | --- | --- |
| A 개선 전 | 4171.0ms | 3471.5ms | 601.0ms |
| B 가드 한 줄 | **2328.0ms** | 1326.5ms | 1021.0ms |
| C 개선 후 | **195.0ms** | 관측되지 않음 | 해당 없음 |

여기서는 이야기가 달라졌습니다. 가드 한 줄로 **1843ms**가 줄었지만 여전히 **2328ms**가 남았습니다. 실험 전에 정해 둔 기준은 "B가 1초 안쪽이면 구독이 주된 원인, 3초 이상 남으면 다른 원인"이었는데, 결과가 그 둘 사이에 떨어져 기준이 판정을 내려주지 못했습니다. 결론은 두 원인이 모두 비슷한 크기로 기여했다는 것입니다.

전송 경로가 수신 경로와 다른 이유는 단계가 하나 더 있기 때문입니다. 개선 전 코드는 Enter를 누르면 먼저 서버에 저장 요청을 보내 응답을 기다리고, 그다음 서버가 되돌려주는 실시간 이벤트를 또 기다린 뒤에야 화면을 그립니다. 구독을 고쳐도 이 왕복 자체는 그대로 남으므로, B에도 **1326.5ms**가 남았습니다. 낙관적 업데이트는 이 왕복을 화면에서 걷어내는 방식입니다.

그래서 **4171ms**를 이렇게 나눌 수 있습니다.

| 줄어든 구간 | 크기 | 무엇이 줄였는가 |
| --- | --- | --- |
| A에서 B로 | **1843ms** | 빈 채널 구독 제거 |
| B에서 C로 | **2133ms** | 낙관적 업데이트가 왕복 대기를, 메모이제이션이 도착 후 렌더를 걷어냄 |

### 개선 후 조건에서는 프레임이 아예 관측되지 않았습니다

C에서는 20회 모두 프레임 도착 시각이 기록되지 않았습니다. 이것은 계측 실패가 아니라 오히려 증거입니다. C는 **195ms**에 이미 화면에 그려졌고, 측정 스크립트는 화면을 확인한 직후 브라우저를 닫으므로 뒤늦게 도착한 이벤트를 볼 기회가 없었습니다. 개선 후 코드가 서버를 전혀 기다리지 않는다는 사실이 이렇게 드러났습니다.

미리 적어 둔 기준에는 "프레임 도착보다 화면 표시가 먼저 일어나면"이라고 썼는데, 실제로는 시간 차가 음수로 나오는 대신 프레임 자체가 잡히지 않는 모양으로 나왔습니다. 기준 문구를 글자 그대로 충족한 것은 아니고, 같은 결론을 다른 형태로 보여준 결과입니다. 사전에 적어 둔 기준이 결과의 모양까지 맞히지는 못한다는 것도 이번에 배운 점입니다.

### 이 실험의 숫자를 위쪽 표와 나란히 놓으면 안 됩니다

C의 **195ms**는 앞서 본 측정에서 나온 **49.2ms**보다 큽니다. 측정 시작점이 달라서 생긴 차이입니다. 본 측정은 브라우저 안에서 키 입력 시각을 직접 기록했지만, 이 실험은 브라우저 밖의 별도 프로세스에서 시각을 재므로 프로세스 사이를 오가는 지연이 섞여 있습니다. 같은 실험 안에서 A와 B와 C를 비교하는 것은 유효하지만, 다른 측정의 절대값과 비교하는 것은 유효하지 않습니다.

### 정리하면

개선은 두 갈래였습니다. 하나는 낙관적 업데이트와 메모이제이션으로 서버 왕복과 렌더 비용을 화면에서 걷어낸 것이고, 다른 하나는 구독 구현을 바로잡아 실시간 이벤트가 늦게 도착하는 문제를 없앤 것입니다. 지난 글에서 저는 첫 번째만 이야기했습니다.

그러나 반대로 두 번째에 모든 것을 귀속하는 것도 틀립니다. 이 글의 앞선 판에서 저는 구독 결함을 체감 지연의 주된 원인으로 썼는데, 실험 결과 그 설명은 메시지를 받는 경로에서만 맞고 보내는 경로에서는 절반만 맞았습니다. **두 번 모두 하나의 원인으로 다 설명하려 한 것이 문제였습니다.**

## ⚠️ 개선되지 않은 것도 있었습니다

모든 지표가 좋아진 것은 아니었습니다. 채팅방에 처음 들어가는 시간은 사실상 그대로였습니다.

| 진입 (300건) | 개선 전 | 개선 후 | 변화 |
| --- | --- | --- | --- |
| 렌더 비용 | 362.7ms | 65.6ms | **81.9% 감소** |
| 진입 완료까지 걸린 전체 시간 | 2351ms | 2138ms | **9.1% 감소** |

렌더 비용은 크게 줄었지만 사용자가 실제로 기다리는 시간은 9.1%만 줄었습니다. 초기 진입 시간은 번들을 내려받고 첫 조회 쿼리를 실행하는 데 대부분을 쓰고, 렌더 비용은 그중 일부이기 때문입니다. 300ms를 아껴도 전체 2.3초 안에서는 티가 나지 않습니다.

왕복 지연을 400ms 추가한 조건에서는 오히려 개선 후가 **421ms 느렸습니다**(4776ms에서 5197ms, p=0.047). 컴포넌트를 분리하면서 번들 크기와 청크 구성이 조금 달라진 영향으로 보이지만, 원인을 확정하지는 못했습니다. 확실한 것은 초기 진입 속도가 이 PR의 개선 대상이 아니었고 실제로도 개선되지 않았다는 사실입니다. 이 부분을 줄이려면 가상 스크롤이나 청크 분할 같은 별도 작업이 필요합니다.

측정 지표 하나를 잘못 고른 것도 기록해 둡니다. `actualDuration`을 `baseDuration`으로 나눈 비율을 메모이제이션 효과의 대리 지표로 쓰려고 했는데, 진입 시나리오에서는 개선 전 1.17, 개선 후 2.98로 거꾸로 나왔습니다. `baseDuration`은 메모이제이션이 없다고 가정했을 때의 렌더 비용 추정값이고, 이 추정은 컴포넌트 트리 구조에 따라 달라집니다. 컴포넌트를 쪼개면 기준 자체가 바뀌므로 두 버전을 이 값으로 비교할 수 없습니다. 그래서 이 지표는 화면이 갱신되는 단계에서만 해석했고, 거기서는 개선 전이 항상 1.00인 반면 개선 후는 0.06에서 0.15 사이로 일관되게 나왔습니다.

## ✨ 회고

이번 검증에서 가장 크게 배운 것은, 개선이 실제로 일어났는지보다 **무엇 때문에 일어났는지를 확인하는 일이 더 어렵다**는 점이었습니다. 지난 글에서 저는 컴포넌트 분리와 메모이제이션, 그리고 낙관적 업데이트로 3~4초를 줄였다고 썼습니다. 세 가지 모두 실제로 효과가 있었으므로 결론은 맞았지만, 비슷한 몫을 차지한 구독 구현 문제는 알아채지 못했습니다.

원인을 잘못 짚는 일이 한 번 더 있었습니다. 이 글의 이전 판에서는 반대로 구독 구현 문제를 체감 지연의 주된 원인으로 썼는데, 그것도 절반만 맞았습니다. 두 번 모두 4초짜리 지연을 원인 하나로 설명하려 한 것이 잘못이었고, 한 줄만 바꾼 조건을 따로 만들어 재 보고 나서야 두 원인의 크기를 구분할 수 있었습니다. **원인을 나누려면 의심하는 곳을 하나만 바꾼 버전이 필요하다**는 것이 이번에 가장 값비싸게 배운 점입니다.

이 사실을 발견할 수 있었던 것은 기각된 가설 하나 덕분이었습니다. 네트워크를 느리게 만들었는데도 개선 폭이 커지지 않는다는 결과를 마주하지 않았다면, 개선 전의 지연이 왕복 시간과 무관하다는 점을 들여다볼 이유가 없었을 것입니다. 예상이 빗나간 지점을 그대로 남겨 둔 것이 결국 원인을 찾는 실마리가 되었습니다.

측정을 시작하기 전에 가설과 판정 기준을 먼저 적어 둔 것도 도움이 되었습니다. 결과를 본 뒤에 기준을 세웠다면, 잘 나온 지표만 골라 놓고 기각된 가설은 조용히 지웠을 가능성이 큽니다. 진입 시간이 개선되지 않았고 지연 네트워크에서는 오히려 느려졌다는 결과 역시 같은 이유로 그대로 실었습니다.

다음 과제는 지난 글에서 언급했던 가상 스크롤입니다. 이번 측정에서 개선 후의 렌더 비용은 메시지 수와 거의 무관해졌지만, 초기 진입 시간은 여전히 메시지가 늘어날수록 함께 늘어납니다. 화면에 보이는 메시지만 렌더하는 방식으로 이 부분을 다시 다뤄볼 계획입니다.

## 확인이 필요한 내용

- 실패한 채널 하나가 왜 다른 채널의 이벤트 전달까지 늦추는지, `supabase-js` 내부의 동작은 규명하지 못했습니다. 결함이 지연을 만든다는 사실은 실측으로 확인했지만 그 안의 기제는 추정에 머물러 있습니다.
- 정리 함수가 전달되지 않아 채널이 쌓이는 문제가 지연에 얼마나 기여했는지는 분리하지 못했습니다. B 조건은 이 문제를 그대로 둔 채로도 수신 지연이 개선 후 수준까지 떨어졌으므로 기여가 작았을 것으로 보이지만, 정리 함수만 고친 네 번째 조건을 만들어 확인하지는 않았습니다.
- 전송 실험에서 B의 "도착 후 화면에 보일 때까지"가 **1021.0ms**로 A의 **601.0ms**보다 컸던 이유를 확인하지 못했습니다. 회차별 변동이 크므로 이 값 위에 추가 결론을 세우지 않았습니다.
- 왕복 지연 400ms 조건에서 개선 후 진입이 421ms 느렸던 원인을 확정하지 못했습니다. 번들과 청크 구성 차이로 추정하고 있습니다.
- 자동 측정은 Headless Shell 기준입니다. 실제 Chrome에서의 절대값은 다를 수 있으며, 두 버전이 같은 브라우저를 썼으므로 비교 자체는 유효합니다.
- 상대 메시지 수신 시간은 메시지를 넣는 쪽과 시간을 재는 쪽의 프로세스가 달라 근사값입니다. 두 조건에 똑같이 섞이므로 비교에는 쓸 수 있으나 절대값은 상한으로 읽어야 합니다.
- `MessageItem`의 렌더 횟수가 0회라는 점은 자동으로 수집하지 못했습니다. `actualDuration / baseDuration` 비율이 대리 지표이며, 개선 후 이 값이 0.06까지 떨어지는 것으로 간접 확인했습니다.
