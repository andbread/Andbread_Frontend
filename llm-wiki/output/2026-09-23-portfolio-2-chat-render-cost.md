# 컴포넌트 분리와 메모이제이션으로 채팅 렌더링 성능 개선

> 포트폴리오 2편입니다. 1편([전송 지연 개선](./2026-09-23-portfolio-1-chat-send-latency-v2.md))과 같은 양식(문제 인식 / 해결 과정 / 결과, 불릿 서술)으로 작성했습니다. 1편이 252ms에서 끊었으므로 이 편이 그 지점을 이어받습니다.

---

## 문제 인식

- 메시지 100건이 쌓인 채팅방에서 **메시지 1건을 보내고 화면에 보일 때까지 목록 전체가 5번 다시 그려져**, 그 렌더 시간의 합이 **914ms**에 달하는 것을 React Profiler로 확인
- 비용이 메시지 수에 비례해 커지는 구조라, 전송 지연을 252ms까지 줄여도 방치하면 사용자가 채팅방을 오래 쓸수록 다시 느려지는 문제
- 입력창에 글자가 들어갈 때도, Enter로 입력창이 비워질 때도 목록 전체가 다시 그려져 **가장 무거운 커밋 하나가 227ms**를 차지했고, 그 구간 동안 입력과 스크롤이 멈추는 문제

## 해결 과정

> **[그림 2] 항목별 렌더 비용 막대** — 개선 전 914.2ms / 시간 포맷만 41.3ms / 분리·메모만 9.3ms / 둘 다 7.7ms. 두 막대의 감소분이 겹치는 871.3ms를 별도 색으로 표시해 효과가 합산되지 않음을 드러냄

- 메시지 목록과 개별 메시지를 한 컴포넌트에서 렌더하던 구조를 `MessageList` / `MessageItem`으로 분리하고, `MessageItem`을 `memo`로 감싸 내용이 바뀐 메시지만 다시 그리도록 변경
- `memo`는 props가 이전과 같아야 효과가 있는데 **각 메시지의 시간 표시를 렌더 중에 매번 새로 계산**하고 있어 매번 다른 값이 들어가던 것을 확인하고, 목록을 만들 때 미리 계산해 문자열로 넘기도록 수정
- 스크롤 위치를 state로 들고 있어 스크롤할 때마다 커밋이 추가로 발생하던 처리를 ref 기반으로 교체
- 개선 항목마다 **한 군데만 다른 빌드를 따로 만들어** 기여도를 분리 측정 (8개 조건 × 20회, 조건 순서 회전, 구독 정상화를 음성 대조군으로 배치)

## 결과

- 전송 1회당 렌더 시간 합 **914.2ms → 5.2ms로 99.4% 감소** (운영 빌드·운영 DB, CPU 4배 제한, 메시지 100건, 조건당 20회 중앙값)
- 가장 무거운 단일 커밋 **226.8ms → 2.8ms**, 커밋 수 5회 → 2회로 감소해 렌더 도중 화면이 멈추는 구간이 사라짐
- 항목별 단독 효과는 분리·메모이제이션 **−904.8ms**, 시간 포맷 사전 계산 **−872.9ms**였고, 두 값의 합이 전체 감소량을 크게 넘음. **871.3ms가 중첩분**으로, 두 항목이 같은 비용을 서로 다른 경로로 제거하기 때문
- 1편에서 남아 있던 전송 체감 지연 **252ms → 51ms**로 감소
- 개선 항목의 효과는 합산되지 않으므로 **따로 재보지 않으면 각각을 과대평가하게 된다**는 것을 배움. 사전에 시간 포맷의 효과를 200~500ms로 예측했으나 실제로는 873ms였음

## 작성 메모 (페이지에는 넣지 않음)

**1편과 끊은 지점**: 1편은 "전송 후 3~4초"를 문제로 잡고 252ms에서 끝냅니다. 이 편은 같은 252ms를 이어받되 문제 인식을 **체감 지연이 아니라 메시지 수에 비례해 커지는 렌더 비용**으로 다시 세웁니다. 두 편의 성과 수치가 겹치지 않으므로 나란히 놓아도 중복으로 읽히지 않습니다.

**핵심 수치를 914ms로 잡은 이유**: 최종 체감 지연 감소분(252 → 51ms)만 쓰면 200ms짜리 개선으로 보입니다. 그러나 실제로 제거한 것은 이벤트 1회당 914ms의 렌더 비용이고, 200ms는 그중 화면에 드러난 부분입니다. **둘을 모두 적되 렌더 비용을 앞에 두는 편이 정확합니다.**

**중첩 871.3ms를 넣은 이유**: 두 개선을 각각 900ms 가까이 줄였다고만 적으면 합쳐서 1.8초를 줄인 것처럼 읽힙니다. 실제 전체 감소량은 909ms입니다. 이 수치를 밝히는 쪽이 측정 설계를 이해하고 있음을 보여 주므로 감점이 아니라 가점 요소입니다.

**그림 2 대안**: 메시지 수(30 / 100 / 300건)에 따른 렌더 비용 선그래프도 후보입니다. 개선 전은 우상향하고 개선 후는 평평하게 누우므로 확장성 서사에 더 맞습니다. 다만 **현재 측정은 100건에서만 했으므로 이 그림을 쓰려면 30건과 300건을 추가로 재야 합니다.**

**넣지 않은 것**: 이 개선이 1편의 4초 지연에는 기여하지 않았다는 사실(p=0.871, p=0.685)입니다. 지표가 다르므로 이 편의 주장과 모순되지 않지만, 설명 없이 적으면 오해를 부릅니다. 면접에서 "그럼 처음부터 렌더를 고쳤으면 됐던 것 아니냐"는 질문이 나올 때 답할 거리로 남겨 둡니다.
