# 구독 로직 개선과 낙관적 업데이트로 채팅 전송 지연 개선

> 포트폴리오 1편 초안입니다. 2편은 컴포넌트 분리와 메모이제이션을 다루며, 이 글의 결과에서 이어집니다.

**한 문장 요약**: 메시지를 보낸 뒤 화면에 반영되기까지 걸리던 **약 4초를 252ms로 줄였고(93.7% 감소)**, 그 지연이 렌더 성능이 아니라 실시간 구독 구현 결함과 서버 왕복 대기에서 왔다는 것을 조건을 하나씩 바꾼 실험으로 확정했습니다.

---

## 🔍 문제 인식

엔빵은 제가 운영하는 구독 공유 정산 서비스입니다. 이 서비스의 채팅방에서 메시지를 보내면 **3~4초가 지나서야 화면에 나타났습니다.** 입력은 즉시 비워지는데 메시지는 한참 뒤에 떠서, 전송이 실패한 것처럼 보이는 상황이었습니다.

처음에는 원인을 두 가지로 짐작했습니다. 하나는 네트워크가 느린 것이고, 다른 하나는 쌓인 메시지를 다시 그리는 비용이 큰 것이었습니다. 둘 다 그럴듯했지만 **어느 쪽인지 확인하지 않은 채로는 무엇을 고쳐야 할지 정할 수 없었습니다.**

그래서 고치기 전에 재현 조건부터 고정했습니다. 운영과 같은 빌드를 띄우고 운영 데이터베이스에 연결한 뒤, 저사양 기기를 가정해 CPU를 4배로 제한하고 메시지를 100건 쌓아 두었습니다. 이 조건에서 개선 전 전송 지연은 **3983.8ms**로 재현됐습니다.

---

## 🧭 원인을 좁혀 나간 과정

### 네트워크도 렌더 비용도 아니었습니다

가장 먼저 한 일은 짐작을 지우는 것이었습니다. 조건을 바꿔 가며 같은 값을 재 보았습니다.

| 개선 전 전송 지연 | 값 |
| --- | --- |
| 지연 없음, 메시지 100건 | 3961ms |
| 왕복 지연 400ms 추가 | 3890ms |
| 메시지 300건 | 3750ms |

**네트워크를 400ms 느리게 만들어도, 메시지를 3배로 늘려도 값이 거의 변하지 않았습니다.** 네트워크가 원인이라면 첫 번째와 두 번째가 달라야 하고, 렌더 비용이 원인이라면 첫 번째와 세 번째가 달라야 합니다. 둘 다 아니었습니다.

이 결과가 원인 추적의 출발점이 되었습니다. **지연이 일의 양이 아니라 고정된 무언가를 기다리는 시간처럼 보였기 때문입니다.**

### 상대가 보낸 메시지도 똑같이 느렸습니다

결정적인 단서는 수신 경로에 있었습니다. 다른 사람이 보낸 메시지를 받는 상황에서도 **4328.5ms에서 462.3ms로** 큰 차이가 났습니다.

이 시나리오에는 내가 보낸 메시지를 미리 그려 두는 방식이 개입할 여지가 없습니다. 그런데도 같은 규모의 지연이 있다는 것은, **보내는 쪽 로직이 아니라 서버에서 오는 이벤트를 받는 경로에 문제가 있다는 뜻**이었습니다.

### 코드에서 원인을 찾았습니다

실시간 구독을 설정하는 부분을 다시 읽었습니다.

```tsx
// 개선 전: nbreadId의 초깃값이 빈 문자열입니다
const [nbreadId, setNbreadId] = useState<string>('')

// async 함수를 호출하므로 정리 함수가 React에 전달되지 않습니다
useEffect(() => {
  subscribeChatRoom()
}, [nbreadId])
```

라우트 파라미터를 상태에 복사해 두는 구조여서, **첫 렌더 시점에는 `nbreadId`가 빈 문자열이었습니다.** 그 상태로 구독 `useEffect`가 먼저 실행되어 `supabase.channel('')`로 접속을 시도했고, 서버는 `TopicNameRequired: You must provide a topic name` 오류로 이 요청을 거절했습니다. 클라이언트는 이 빈 채널에 접속과 해제를 반복했습니다. WebSocket 프레임을 직접 열어 확인한 내용입니다.

여기에 더해 `useEffect`에 넘긴 함수가 async였기 때문에 **정리 함수가 React에 전달되지 않아 채널이 해제되지 않고 쌓였습니다.**

## 🛠 해결

두 가지를 고쳤습니다. 성격이 다른 두 문제였기 때문입니다.

### 1. 실시간 구독 정상화

라우트 파라미터를 상태에 복사하지 않고 `useMemo`로 직접 유도해, **빈 문자열 구간 자체를 없앴습니다.** 값이 없는 경우를 막는 가드를 두고, 구독 함수에서 async를 걷어내 정리 함수가 정상적으로 반환되도록 했습니다.

```tsx
// 개선 후
const nbreadId = useMemo(() => {
  const routeNbreadId = params.nbreadId
  return typeof routeNbreadId === 'string' ? routeNbreadId : ''
}, [params.nbreadId])

useEffect(() => {
  if (!nbreadId) {
    return
  }

  const channel = supabase
    .channel(nbreadId)
    .on('postgres_changes', { /* ... */ }, (payload) => { /* 병합 */ })
    .subscribe()

  return () => {
    supabase.removeChannel(channel)
  }
}, [nbreadId])
```

### 2. 낙관적 업데이트

구독을 고쳐도 **서버에 저장 요청을 보내고 응답을 기다리는 시간은 그대로 남습니다.** 개선 전에는 저장이 끝난 뒤 서버가 되돌려주는 이벤트를 받아야만 화면이 갱신됐기 때문입니다.

그래서 전송 즉시 임시 메시지를 목록에 넣어 먼저 그리고, 저장이 끝나면 실제 메시지로 바꾸도록 했습니다. 실패하면 되돌리고 사용자에게 알립니다. 서버가 되돌려주는 이벤트가 도착했을 때 메시지가 중복되지 않도록 병합 로직을 함께 넣었습니다.

## 🧪 원인을 확정하는 방법

여기까지는 정황이 맞아떨어졌을 뿐, **인과를 확인한 것은 아니었습니다.** 빈 문자열 구독은 채팅방에 들어가는 순간에 한 번 일어나는 사건인데, 측정은 화면이 다 그려지고 5초를 기다린 뒤에 진행했습니다. 진입 시점의 한순간이 5초 뒤의 4초 지연을 만든다는 설명을 그대로 받아들일 수는 없었습니다.

그래서 **개선 전 코드에 가드 한 줄만 추가한 세 번째 버전**을 따로 만들었습니다. 메모이제이션도 낙관적 업데이트도 없는 개선 전 코드 그대로이고, 오직 `if (!nbreadId) return` 한 줄만 다릅니다.

| 조건 | 이벤트 도착까지 |
| --- | --- |
| 개선 전 | 4219ms |
| **개선 전 + 가드 한 줄** | **520ms** |
| 개선 후 | 536ms |

가드 한 줄만으로 개선 후와 같은 수준이 되었습니다. `TopicNameRequired` 오류 프레임도 개선 전에는 회차마다 2건씩 관측되다가 두 조건에서는 한 건도 나오지 않았습니다.

**한 군데만 다른 버전을 만들어야 그 한 군데가 원인이라고 말할 수 있습니다.** 여러 가지를 한 번에 바꾼 상태에서는 어떤 변경이 효과를 냈는지 알 수 없습니다.

## 📊 결과

각 항목만 개선 전 코드에 적용해 측정한 값입니다. 조건당 20회 반복한 중앙값입니다.

| 조건 | 전송 체감 지연 | 개선 전 대비 |
| --- | --- | --- |
| 개선 전 | 3983.8ms | 기준 |
| **구독 정상화만 적용** | **1007.1ms** | **−2976.8ms (74.7%)** |
| **낙관적 업데이트만 적용** | **251.7ms** | **−3732.1ms (93.7%)** |

두 개선을 단계로 보면 이렇게 이어집니다.

```
3984ms ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  개선 전
          ↓ 빈 채널 구독 제거          −2977ms
1007ms ━━━━━━━━━━
          ↓ 서버 왕복을 화면에서 제거   −755ms
 252ms ━━▌
```

수신 경로에서도 이벤트 도착이 **4219ms에서 520ms로** 줄었습니다. 이쪽은 낙관적 업데이트가 관여할 수 없는 경로이므로, **구독 정상화만의 효과입니다.**

측정 결과는 모두 p < 0.001이고 효과 크기는 1.00이었습니다. 개선 전 20회와 개선 후 20회의 값이 범위조차 겹치지 않았다는 뜻입니다.

> 측정 조건: 운영 빌드와 운영 데이터베이스 · 메시지 100건 · CPU 4배 제한 · 조건당 20회 중앙값 · 조건 순서를 회차마다 교차

## 💡 배운 것

**지연의 정체가 일의 양인지 기다림인지 먼저 갈라야 합니다.** 이 문제를 처음 마주했을 때 저는 렌더 성능을 의심했고, 실제로 컴포넌트 분리와 메모이제이션을 함께 적용했습니다. 나중에 항목별로 다시 측정해 보니 **렌더 최적화가 이 4초에 기여한 몫은 통계적으로 검출되지 않았습니다.** 4초의 대부분은 기다리는 시간이었고, 렌더는 그 기다림 안에서 처리되어 전체 시간을 늘리지 않았기 때문입니다.

**원인을 특정하려면 한 군데만 다른 버전이 필요합니다.** 개선 전후를 비교하면 얼마나 좋아졌는지는 알 수 있지만 무엇 때문에 좋아졌는지는 알 수 없습니다. 가드 한 줄만 추가한 조건을 따로 만들고 나서야 원인을 확정할 수 있었습니다.

**측정 조건을 먼저 고정하지 않으면 결과를 신뢰할 수 없습니다.** 처음 이 개선을 진행할 때는 개발 서버에서 스크린샷 몇 장으로 마무리했는데, 그 값으로는 분산도 원인도 알 수 없었습니다. 운영과 같은 빌드, 명시한 CPU 제한, 반복 횟수, 조건 교차 실행을 갖추고 나서야 이 글의 수치들이 나왔습니다.

## 시각화 자리

1. **워터폴 차트**: 3984 → 1007 → 252ms 두 단계. 두 감소분에 같은 색 계열을 써서 둘 다 기다리는 시간이었음을 드러냅니다.
2. **3조건 비교 막대**: 4219 / 520 / 536ms. 가운데 막대에 `if (!nbreadId) return` 코드를 표기합니다.
3. **조건 무관성 막대(선택)**: 3961 / 3890 / 3750ms 세 막대가 거의 같은 높이인 그림입니다.
